## Context

См. `proposal.md` и `specs/ai-context-and-prompts/spec.md` для мотивации и поведенческого контракта. Сейчас chat-generation и guest-generation получают динамически скомпилированный prompt из Langfuse, а текущий transport разделяет системные инструкции и обычную историю сообщений. В базе уже есть сообщения и nullable `sessionId`, но идентичность AI-треда и синтетические блоки user-context/vector search не образуют восстанавливаемый журнал.

## Goals / Non-Goals

**Goals:**

- Сделать стабильный prefix для одного AI-треда и сохранять его настройки.
- Воспроизводить контекст после рестарта без повторной сборки старых динамических блоков.
- Сохранить текущие правила поведения, voice/image-контракты, fact-анализ и Langfuse tracing.
- Перевести runtime prompt management в локальный типизированный реестр с тестами точного текста.
- Получить измеримые cache read/write и latency-сигналы без утечки содержимого.

**Non-Goals:**

- Не добавлять новый кэш-сервис, Redis или зависимость от конкретной функции `cache_control` провайдера.
- Не менять алгоритм vector search, его фильтры, embedding-модели или performance budget.
- Не менять пользовательские квоты, правила приватности и формат Telegram-ответов.
- Не делать Langfuse необязательным для tracing в рамках этого change и не удалять его конфигурацию только из-за удаления prompt fetching.

## Decisions

### 1. Хранить отдельный AI-тред и append-only журнал

Добавить минимальную пару сущностей в Prisma:

- `AiThreadContext` — стабильный идентификатор треда, связь с chat/root-message, локальная версия prompt, случайные правила, текущий cache boundary и timestamps.
- `AiThreadContextEvent` — монотонный `sequence`, тип события, ссылка на обычное сообщение либо JSON-снимок синтетического контекста и идентификатор turn для идемпотентности.

События нужны только для того, что нельзя надёжно восстановить из обычной истории сообщений. Сами пользовательские и assistant-сообщения остаются в существующем repository и получают ссылки из журнала. JSON payload используется для immutable snapshot результатов поиска, user-context и correction; это предотвращает изменение старого запроса при изменении текущих фактов.

Альтернатива — хранить весь контекст одним JSON-полем в `Message` или пересобирать его из текущего состояния. Первый вариант создаёт большие конкурентные записи, второй ломает append-only prefix, поэтому выбран журнал с короткими ссылками на сообщения и snapshot только синтетических блоков.

Идентичность треда берётся из существующей reply/session-семантики: корневой AI-запрос создаёт идентификатор, а последующие ответы в его reply chain используют тот же идентификатор. `sessionId` сообщений должен действительно сохраняться, чтобы после рестарта не зависеть от памяти процесса. Новые независимые запросы начинают новый тред.

### 2. Собирать запрос в два слоя

Для каждого запроса сборщик формирует:

1. неизменяемые системные инструкции из локального `chat-generation` base и сохранённых правил треда;
2. append-only историю из ранее записанных событий, новых context-событий текущего turn, текущего user message и доступного assistant history.

Порядок первого и последующих turn выглядит так:

```text
instructions(base + thread rules)
CONTEXT(users/facts initial)
CONTEXT(retrieval 1)
USER 1
ASSISTANT 1
CONTEXT(retrieval 2)
CONTEXT(new users/facts delta)
USER 2
```

Новый retrieval-блок не заменяет предыдущий. Если изменение факта противоречит старому snapshot, добавляется correction-событие, а общие инструкции объясняют приоритет более позднего события.

Текущее время и другой быстро меняющийся turn-specific контекст не входят в стабильные инструкции. Они добавляются непосредственно к текущему turn, иначе каждый запрос инвалидировал бы общий prefix. Список пользователей добавляется целиком только при первом запросе и затем — дельтами.

### 3. Не использовать системную роль для исторических событий

Оставить системную роль только для верхнеуровневых инструкций, которые транспорт передаёт через `instructions`. Синтетические события истории сериализовать как обычные структурированные сообщения допустимого типа с явным маркером контекста и sequence. Это сохраняет порядок в истории и не конфликтует с текущим удалением system-сообщений из `messages` перед вызовом модели.

Альтернатива — добавлять новый system prompt в середину диалога. Она не подходит: текущая реализация и provider API не дают гарантии, что такая роль останется на месте, а иногда отклоняют её.

### 4. Сделать локальный prompt registry без общего шаблонизатора

Создать один небольшой модуль/каталог локальных промптов с типизированными идентификаторами, статическими строками, рендерингом известных переменных и локальной версией. Не добавлять Mustache-подобную зависимость: текущих переменных достаточно для простых функций.

`chat-generation` хранится как статический base с согласованным русским текстом, а `rules`, `time`, `users` и история оформляются сборщиком контекста. `voice-summarize` поддерживает `author`; остальные промпты не получают произвольные внешние переменные.

Текст текущего Langfuse `meta-analyzer` v2 фиксируется как snapshot без редакторской правки. Runtime-использование активного fact-анализатора сохраняет его отдельное требование к `facts`, `content`, `type` и `sourceMessageId`. Legacy-модуль, который писал пятикомпонентный результат в `User.metaInfo`, больше не вызывается и удаляется после проверки ссылок.

### 5. Оставить Langfuse только для наблюдаемости

Существующие traces и связи с генерациями сохраняются. Вместо тела remote prompt в trace передаются `promptId`, локальная версия/короткий hash, `threadId`, cache boundary и token/latency usage, если их вернул провайдер. Для диагностики raw prompt не логируется.

### 6. Обеспечить идемпотентную запись turn

Добавление новых событий и привязка текущего user message выполняются одной транзакцией с уникальным ключом `(threadId, turnId, eventKind)`. Повторная доставка Telegram update или retry генерации не должны дублировать retrieval/user-context события. Assistant event добавляется только после успешной генерации и сохранения ответа; незавершённый turn остаётся повторяемым.

### 7. Сбрасывать cache boundary только при компактизации

До достижения контекстного лимита журнал воспроизводится полностью. При компактизации сборщик создаёт snapshot актуального состояния и новый boundary, сохраняет связь с предыдущей цепочкой и начинает новый append-only segment. Сброс не должен происходить на каждом сообщении и должен быть виден в метриках.

## Risks / Trade-offs

- **[Риск]** Append-only snapshots увеличивают размер базы и запросов на длинных тредах → **Митигировать** ограничением размера payload, ссылками на существующие сообщения, retention-правилами и редкой компактизацией по лимиту контекста.
- **[Риск]** Два параллельных сообщения одного треда могут получить одинаковый sequence → **Митигировать** транзакцией, уникальным sequence в рамках треда и идемпотентным `turnId`.
- **[Риск]** Перенос времени и пользователей из исходного шаблона может изменить приоритет инструкций → **Митигировать** snapshot-тестами итоговой структуры prompt и regression-тестом ответа/схемы для каждого caller.
- **[Риск]** Провайдер не вернёт cache read/write → **Митигировать** разделением локальных метрик prefix/hash и явным значением `unavailable`, без ложного вывода о cache miss.
- **[Риск]** Удаление legacy-метааналитики выявит скрытый внешний импорт → **Митигировать** поиском всех callers, typecheck и тестом миграции до удаления файла.
- **[Риск]** Синтетический контекст содержит персональные данные → **Митигировать** существующими retention/privacy-правилами, хранением только необходимого snapshot и запретом raw prompt в логах/метриках.

## Migration Plan

1. Добавить обратимо совместимую Prisma migration для AI-тредов и событий, не удаляя старые поля и `User.metaInfo`.
2. Выпустить локальный prompt registry и переключить callers с `getPrompt`, сохранив traces.
3. Начать создавать новые треды через журнал; существующие активные треды при продолжении получить начальный checkpoint из доступной истории и текущего контекста.
4. Включить безопасные cache-метрики и сравнить первый/последующие запросы до изменения порогов компактизации.
5. После проверки callers и миграции старого `User.metaInfo` удалить только неиспользуемый legacy-анализатор.

Rollback выполняется возвратом приложения на предыдущую версию: новые таблицы и данные не удаляются, старый код продолжает работать со своей историей. Деструктивное удаление legacy-данных в change не выполняется.

## Open Questions

Нет вопросов, способных изменить выбранный контракт или архитектуру; детали имен Prisma-полей и конкретного формата event payload уточняются при реализации без изменения требований.
