## Context

Мотивация описана в `proposal.md`. В текущем checkout `scheduleUserMessageAnalysis` создаёт `USER_MESSAGE_ANALYSIS` каждые 30 публичных сообщений автора в чате; worker резервирует квоту `ANALYSIS` и читает последние 30 сообщений с reply. `analyzeUserMetaInfo` извлекает `facts` только об авторе, а проверка источника требует совпадения автора факта с автором сообщения. Ослаблять эту проверку для псевдонимов нельзя: у наблюдения «Санёк, привет» автор и адресат различаются.

Поиск автора находится в `resolveSender` внутри `src/ai/tools/chat-history.ts`; `get_user_info` принимает ID и отдельно подтверждает текущее участие другого пользователя через Telegram. Обычный AI-контекст содержит автора, участников reply-истории и Telegram-упоминания. Динамические сведения сохраняются через append-only события; старое имя может остаться в истории и compaction snapshot.

## Goals / Non-Goals

**Goals:**
- Проверяемая связь псевдонима с ID, несколько имён на человека, независимые значения в разных чатах.
- Один путь разрешения пользователей для tools и явный приоритет исправлений владельца в ответах.
- Повторяемое накопление уверенности при повторной доставке, параллельных jobs и overlapping batches.

**Non-Goals:**
- Отдельный сервис, очередь, LLM-вызов на каждое сообщение или новый векторный индекс.
- Автоматический backfill всей переписки, общий словарь между чатами, распознавание людей по одному сходству имён.
- Морфологический движок, автоматическое затухание по времени, административный интерфейс и право менять чужое обращение.

## Decisions

### 1. Две таблицы вместо свободного текста в UserFact

`UserAlias` хранит `id`, `chatId`, `userId`, `alias`, `normalizedAlias`, `confidence`, `confirmationCount`, `status` (`CANDIDATE`, `CONFIRMED`, `REJECTED`), `ownerConfirmed`, `addressingBlocked`, `preferred`, timestamps. `confidence` — накопленный рейтинг связи, не статистически калиброванная вероятность. `confirmationCount` — число зачтённых наблюдений, а не запусков анализатора.

`UserAliasEvidence` хранит `aliasId`, составной источник `(sourceChatId, sourceMessageId)`, оценку модели `modelConfidence` и `neutralForAddressing`. Автор и время берутся из исходного сообщения. Все автоматические источники — неприватные пользовательские сообщения текущего чата. На источник действует FK с каскадным удалением; новые связи с `User`/`Chat` также каскадные.

Ограничения: уникальность `(chatId, userId, normalizedAlias)` и `(aliasId, sourceChatId, sourceMessageId)`, проверка диапазона confidence в приложении и БД, индекс `(chatId, normalizedAlias)`. Частичный уникальный индекс разрешает не более одного `preferred = true` на `(chatId, userId)`; новый выбор и снятие старого выполняются транзакционно. Нет глобальной уникальности псевдонима.

Нормализация: Unicode NFKC, trim, схлопывание пробелов, нижний регистр и `ё → е`; отображаемое написание сохраняется. Пустые строки, управляющие символы, значения длиннее 64 Unicode code points и строки, похожие на ID/`@username`, отвергаются. Псевдоним передаётся модели как данные, а Telegram-вывод использует действующее экранирование.

Альтернатива — строка «его называют Санёк» в `UserFact` — не даёт точной уникальности, проверки неоднозначности и независимого управления обращением. Отдельная таблица общих пользовательских предпочтений пока не нужна.

### 2. Дополнение существующего анализа

В том же structured generation добавить массив `aliases` рядом с неизменным `facts`. Наблюдение содержит `userId`, `alias`, `confidence`, `sourceMessageId`, `neutralForAddressing`. Кандидаты адресатов ограничены автором и известными пользователями из предоставленного публичного контекста сообщений/reply; ID не выводятся из догадки модели. В первой версии надёжно поддерживаются самоназывание и обращения в reply. Без известного адресата наблюдение пропускается. Не сохранять новые Telegram entities и не строить каталог всех участников ради этого change.

Передавать в анализ публичные reply-родители с ID авторов; приватный родитель не попадает в prompt. Модель различает обращение к адресату и разговор о третьем лице: reply сам по себе не доказывает принадлежность имени. `alias` должен присутствовать в исходном тексте после нормализации; модель не создаёт необоснованные варианты имени. Падежные формы могут храниться отдельными наблюдаемыми вариантами; при поиске модель может попробовать базовую форму, но нечёткое совпадение не устанавливает ID.

Runtime валидирует finite confidence в `[0, 1]`, известный ID, публичный источник текущего batch, наличие псевдонима в тексте и отсутствие bot-authored источника/бота-адресата. Наблюдения с confidence ниже `0.5` не сохраняются. Непригодное отдельное наблюдение пропускается без потери валидных фактов; для структурно некорректного ответа сохраняется существующий failure/retry lifecycle job. Текущая проверка источников `facts` остаётся неизменной.

Обработка использует существующий шаг в 30 сообщений и ту же квоту `ANALYSIS`. Полная история не перечитывается. Поэтому пассивное обучение имеет задержку и не гарантирует обработку каждого сообщения при overlapping batches. Явные обращения через tool не ждут фонового анализа. Это осознанная граница первой версии; отдельный cursor/stream нужен только при требовании полного покрытия.

### 3. Уверенность и независимость подтверждений

Стартовые параметры реализации, выбранные для первой версии:
- Минимальная уверенность принимаемого наблюдения: `0.5`.
- Первое зачтённое наблюдение задаёт `c = p`; каждое следующее: `c = c + (1 - c) * p * 0.25`.
- Автоматическое подтверждение для поиска: `c >= 0.8` и минимум два разных автора.
- Автоматическое обращение: `c >= 0.9`, минимум два разных автора, все зачтённые наблюдения нейтральны для обращения и нет запрета владельца.

Внутри одной связи засчитывается не более одного наблюдения от автора за календарные сутки Europe/Moscow: самое раннее по `(sentAt, messageId)`. Все валидные источники сохраняются для проверки; остальные за эти сутки не усиливают рейтинг. Разные авторы в тот же день учитываются независимо. Так повтор одного человека слабее нескольких независимых обращений и сам по себе не подтверждает псевдоним.

Агрегат воспроизводимо пересчитывается из уникальных источников в хронологическом порядке. Например, четыре зачтённых наблюдения с `p = 0.8` дают `0.8`, `0.84`, `0.872`, `0.8976`; пятое — `0.91808`. Округление нужно только при отображении. `ownerConfirmed` задаёт confidence `1` без требования двух авторов; пользовательское подтверждение не превращается в фиктивное LLM-наблюдение.

Запись evidence и обновление агрегата выполняются в одной транзакции с сериализацией по строке связи. Повтор источника не меняет исходную оценку модели. После удаления источников чтение связи сверяет/пересчитывает агрегат по оставшимся публичным evidence; устаревший persisted confidence не допускает подтверждение без источников. Для небольшого словаря это достаточно; инкрементальные summary-таблицы не нужны.

`REJECTED`, `addressingBlocked` и явный `preferred` — устойчивые решения владельца. Автоматические jobs их не отменяют и не повышают уверенность отклонённой связи. Снятие отклонения возможно только новой явной просьбой владельца.

### 4. Общий поиск без изменения авторизации

Вынести текущую логику разрешения автора в функцию, используемую историей и `get_user_info`. Сохранить вход `userId` у `get_user_info`, добавить альтернативный `query`; одновременное указание обоих — ошибка, отсутствие обоих по-прежнему означает текущего пользователя. `sender` в истории остаётся совместимым.

Порядок: точный ID/явный `@username`; затем точные имя, фамилия, полное имя, username без `@` и подтверждённые псевдонимы текущего чата; затем частичные совпадения для уточнения. Дедупликация по ID выполняется до оценки числа кандидатов. Не разрешать пустой запрос и не обрезать набор так, чтобы неоднозначность стала единственным совпадением. Ограничивать возвращаемый список с явным признаком усечения.

Одно точное совпадение разрешается; несколько точных совпадений требуют уточнения независимо от разницы confidence. Частичное совпадение или неподтверждённый псевдоним могут дать только кандидатов, не готовый ID. Кандидат с низкой уверенностью не выдаётся за установленную связь.

История продолжает работать с публичными сообщениями текущего чата, включая исторических авторов. `get_user_info` проверяет текущее членство через Telegram до раскрытия чужого профиля, псевдонимов или фактов; то же относится к выдаваемому списку кандидатов. В личке нельзя искать чужих людей через новый параметр. Ошибка проверки не расширяет доступ.

Альтернатива — скармливать модели словарь всего чата на каждый запрос — увеличивает контекст и смешивает разрешение ID с доступом к данным. Tools получают общий поиск по необходимости; текущий контекст получает псевдонимы только уже доступных пользователей.

### 5. Обращение и команды владельца

Добавить writable tool `set_my_alias` с `alias` и `action`: `prefer`, `avoid_addressing`, `reject_identity`. Пользователь и чат берутся исключительно из `BotContext`, параметра чужого ID нет. Tool вызывается только по явной просьбе текущего пользователя, не на основании цитаты или чужой инструкции. В guest/read-only режимах отсутствует; ошибки записи возвращаются как ошибки, бот не сообщает об успешном сохранении заранее.

Уточнение владельца продукта при apply: для падежных форм («не называй меня Шуриком») LLM выбирает существующий псевдоним («Шурик») из контекста текущего пользователя и чата. Код проверяет явную просьбу в текущем сообщении, владельца и scope; морфологический движок не добавляется. Новое имя должно присутствовать в самой просьбе, а существующее передаётся в tool в сохранённом написании.

- `prefer`: подтвердить связь владельцем, снять её отклонение/запрет обращения, назначить единственным предпочтительным именем текущего чата.
- `avoid_addressing`: сохранить запрет обращения, снять `preferred`; уже подтверждённая связь остаётся доступной для поиска. Сам запрет не подтверждает ранее неизвестную связь.
- `reject_identity`: отклонить связь и снять `preferred`; она исключается из поиска и обращения. Для ещё неизвестного имени сохранить запрет, чтобы поздний background job не создал его снова.

Повтор одного действия идемпотентен. Конкурирующие явные изменения упорядочиваются по исходным Telegram message ID внутри чата; старый retry не перезаписывает более новую просьбу. Для этого хранить ID последней явной операции на строке, а смену предпочтения сериализовать по `(chatId, userId)` с проверкой последней операции по всем строкам пары. Явные настройки не должны каскадно удаляться вместе с private-сообщением: они являются намеренно сохранёнными данными, источник операции хранится как ID без FK на сообщение.

Выбор обращения: доступное явное `preferred`; иначе подтверждённый нейтральный псевдоним с `c >= 0.9` и двумя авторами; иначе Telegram firstName/userName. При равенстве рейтинга — больше зачтённых подтверждений, затем более свежее наблюдение, затем стабильный порядок нормализованного имени. Имя, которое точно принадлежит человеку, может оставаться непригодным для обращения; `neutralForAddressing = false` и сомнения модели исключают автоматическое использование.

Порог и веса — именованные константы, не новая пользовательская конфигурация. Самостоятельно выбранное допустимое имя не требует социальной популярности; существующие правила безопасности текста остаются в силе.

### 6. Актуальность AI-контекста

В user context передавать ID, доступные псевдонимы, их confidence, выбранное обращение и запреты текущего чата. Псевдонимы не являются инструкциями. Изменения попадают в последующее `USER_CONTEXT`/`CORRECTION`; последняя настройка имеет приоритет над старым текстом и compaction summary. Обновление через writable tool применяется уже к ответу текущего запроса через результат tool.

В обычном, гостевом и fallback пути передача сведений соблюдает scope и существующие ограничения tools. Из личной переписки ничего не экспортируется в группу. При отклонении связи обновление содержит явное удаление/запрет, чтобы отсутствие строки не оставляло старый псевдоним действующим. Стабильные правила старого треда не переписываются; применимость свежего исправления проверяется на уже существующем треде.

## Risks / Trade-offs

- Уверенность LLM завышена → независимые авторы, подтверждённый источник, минимальные пороги и возможность исправления; число не представляется вероятностью.
- Несколько людей повторяют неприятное прозвище → отдельная нейтральность для обращения и безусловный приоритет запрета владельца. Ошибки классификации полностью не исключаются.
- Reply говорит о третьем лице → контекстная классификация, ограниченный набор ID, пропуск сомнительных случаев, отрицательные примеры в проверках.
- Повторные доставки и гонки → уникальный источник, транзакции, воспроизводимый пересчёт и упорядочивание явных команд.
- Старое имя остаётся в треде → явные correction-события, актуальные запреты и проверка после compaction/restart.
- Небольшой/тихий чат редко достигает порогов → явное самоназывание работает сразу; для автоматического обучения сохраняется текущая задержка анализа.
- Пороги не откалиброваны на реальной переписке → зафиксировать стартовые значения и прогнать синтетические положительные/отрицательные диалоги; изменение порогов после review — отдельная явная корректировка решения.

## Migration Plan

1. В apply добавить аддитивную Prisma-миграцию двух таблиц и ограничений. Не преобразовывать `UserFact`, не заполнять псевдонимы из старых фактов и не менять чужие незакоммиченные OpenSpec-файлы.
2. Проверить миграцию на отдельной тестовой PostgreSQL, сгенерировать клиент и выполнить проверки задач. Накопление начинается из текущих batches после включения новой версии.
3. Доставка в production требует отдельного запроса пользователя. При такой доставке сначала применить совместимую миграцию, затем обновить приложение.
4. Откатить приложение на прежнюю версию без удаления таблиц: старый код их не использует, собранные псевдонимы и решения владельцев сохраняются.
