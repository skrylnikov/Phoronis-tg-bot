## MODIFIED Requirements

### Requirement: Метаанализ использует UserFact без legacy JSON

Система MUST сохранить без замены текст текущей версии `meta-analyzer` из Langfuse, включая пять категорий `interests`, `communication_style`, `notable_traits`, `topics` и `notes`, правила увеличения `weight` для подтверждённых элементов и добавления новых элементов с `weight = 1`. Активный анализ пользовательских фактов MUST сохранять действующий контракт массива `facts` с полями `content`, `type` и `sourceMessageId`; ранее выполненный перенос промпта не меняет этот контракт. После подтверждённого переноса исторических данных система MUST хранить пользовательские факты в `UserFact` и MUST NOT поддерживать отдельный runtime- или migration-путь через legacy JSON `User.metaInfo`.

Результат активного анализа MUST дополнительно содержать отдельный массив `aliases` с предполагаемым адресатом, псевдонимом, уверенностью модели, исходным сообщением и пригодностью для нейтрального обращения. Инструкции этого расширения MUST принадлежать репозиторию и дополнять действующий анализ без подмены `facts`. Псевдонимы MUST обрабатываться по правилам `chat-user-aliases`; наличие адресата, отличного от автора, MUST NOT ослаблять проверку авторства источников обычных фактов.

#### Scenario: Активный анализ извлекает факты
- **WHEN** плановая обработка запускает анализ сообщений пользователя
- **THEN** результат сохраняет действующий формат `facts`, а каждый новый факт сохраняет подтверждённый источник через `sourceMessageId`
- **AND** псевдонимы передаются отдельно в `aliases`, который пуст при отсутствии наблюдений

#### Scenario: Историческая миграция завершена
- **WHEN** проверка данных подтверждает отсутствие неперенесённого `User.metaInfo`
- **THEN** приложение запускается и анализирует факты без legacy JSON и фоновой migration-задачи

#### Scenario: Автор обращается к другому участнику
- **WHEN** автор сообщения использовал псевдоним известного адресата
- **THEN** наблюдение может относиться к адресату, а обычные факты по-прежнему требуют источник от пользователя, которому принадлежат

## ADDED Requirements

### Requirement: Контекст отражает актуальные псевдонимы и предпочтения обращения

Система MUST передавать для доступных в текущем запросе пользователей псевдонимы текущего чата, уверенность, выбранное обращение и запреты как структурированные данные, а не инструкции. Изменения MUST передаваться в последующих событиях обновления/исправления без переписывания старых событий или сохранённых правил треда. Новейшее предпочтение, запрет или отклонение MUST иметь приоритет над старыми именами в сообщениях и summary. Результат явного изменения MUST применяться уже в текущем ответе. Обычный, гостевой и fallback путь MUST соблюдать те же границы чтения, сохраняя существующие ограничения writable tools.

#### Scenario: Пользователь запретил старое обращение
- **WHEN** в существующем треде «Шурик» заменён на «Саша» или запрещён
- **THEN** последующие ответы используют актуальное решение даже при наличии «Шурик» в старых контекстных событиях

#### Scenario: Исправление прошло compaction и рестарт
- **WHEN** после изменения обращения контекст сжат и приложение перезапущено
- **THEN** актуальное предпочтение и запреты сохраняют приоритет и старый псевдоним не восстанавливается из summary

#### Scenario: Имя выглядит как инструкция
- **WHEN** сохранённый псевдоним содержит текст, похожий на команду модели
- **THEN** контекст трактует его только как имя, не меняя системные правила и полномочия tools
