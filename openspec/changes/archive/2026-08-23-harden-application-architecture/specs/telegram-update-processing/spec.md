## Purpose

Надёжно принимает и обрабатывает Telegram updates при временных сбоях, долгих AI-операциях, повторной доставке webhook и параллельной работе нескольких workers.

## ADDED Requirements

### Requirement: Обработка update имеет явный итог

Система SHALL различать успешно завершённый, повторяемый и терминально неуспешный результат обработки update. Ошибка, которая не привела к завершённому пользовательскому или системному результату, MUST NOT silently считаться успешной.

#### Scenario: Временный сбой обработки

- **WHEN** обработка update завершается временной ошибкой базы данных, Telegram API или AI-провайдера
- **THEN** update остаётся доступным для повторной обработки с ограниченным числом попыток и задержкой

#### Scenario: Исчерпаны попытки

- **WHEN** повторяемая ошибка сохраняется после установленного числа попыток
- **THEN** update переводится в терминальное failed-состояние с причиной, а worker не пытается обрабатывать его бесконечно

#### Scenario: Ошибка поглощена пользовательским fallback

- **WHEN** обработчик отправляет fallback-ответ пользователю и считает update завершённым
- **THEN** update помечается completed только после успешной доставки fallback-ответа и сохранения необходимых данных

### Requirement: Lease защищает долгую обработку

Система MUST сохранять эксклюзивное владение обрабатываемым update на всём протяжении допустимой операции. Worker, потерявший lease, MUST NOT завершать или повторно планировать update как будто он всё ещё владеет им.

#### Scenario: Обработка дольше первоначального lease

- **WHEN** AI или другая операция продолжается дольше первоначального lease
- **THEN** активный worker продлевает lease либо операция отменяется до его истечения

#### Scenario: Просроченный worker завершает работу

- **WHEN** lease worker истёк и update был передан другому worker
- **THEN** первый worker не может изменить итоговое состояние update и не создаёт второй пользовательский результат

### Requirement: Updates с общей partition не выполняются конкурентно

Система MUST обеспечивать взаимное исключение для updates, которые относятся к одной chat/user partition и могут менять общее состояние. Приоритет urgent MAY влиять на выбор следующего ожидающего update, но MUST NOT создавать конкурентную обработку конфликтующих updates.

#### Scenario: Обычный и urgent update одного чата

- **WHEN** в одной partition одновременно находятся обычный update и payment/callback update
- **THEN** только один конфликтующий update выполняется в каждый момент времени, а выбранный порядок фиксируется worker-логикой

#### Scenario: Updates разных чатов

- **WHEN** ожидают updates разных partition
- **THEN** система может обрабатывать их параллельно в пределах доступных workers

### Requirement: Повторная доставка не дублирует side effects

Система SHALL быть идемпотентной для повторно принятого Telegram update: повторная доставка одного update не создаёт дубликат сообщения, платежного состояния или пользовательского ответа.

#### Scenario: Webhook повторно отправляет тот же update

- **WHEN** один и тот же `update_id` поступает в webhook более одного раза
- **THEN** он сохраняется или распознаётся как duplicate без создания второго processing intent

#### Scenario: Retry после частичного успеха

- **WHEN** внешний ответ был доставлен, но worker завершился ошибкой до отметки update completed
- **THEN** повторная попытка распознаёт уже выполненный side effect и не отправляет дубликат
