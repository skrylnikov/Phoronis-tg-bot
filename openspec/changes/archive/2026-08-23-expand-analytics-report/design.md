## Context

См. `proposal.md` — Why. Текущий `src/analytics.ts` уже строит вечерний отчёт по московскому дню и использует `Message`, `QuotaUsage`, `PaymentOrder`, `Subscription` и `DailyAnalytics` для идемпотентности. В `Message` пока нет идентификатора модели; обычный AI-контроллер выбирает основную или fallback-модель и сохраняет успешный ответ после доставки. Векторный поиск возвращает массивы пользовательского и чатового контекста, а `/ask` сохраняет отдельные privacy-границы.

## Goals / Non-Goals

**Goals:**

- Иметь один сборщик snapshot-данных для автоматического и ручного отчёта.
- Получать точную модель успешно сохранённого обычного AI-ответа.
- Считать устойчивые к рестарту показатели из базы, а runtime-показатели честно маркировать.
- Сбрасывать только векторные runtime-счётчики при наступлении новой московской даты.
- Сохранить агрегированный и privacy-safe формат отчёта.

**Non-Goals:**

- Не сохранять тексты prompts, ответов, фактов или vector context ради аналитики.
- Не смешивать ephemeral `/ask` с обычной историей `Message` и не менять его retention/privacy-контракт.
- Не добавлять отдельную таблицу событий для vector context.
- Не восстанавливать потерянные после рестарта RAM-метрики задним числом.
- Не менять правила квот, выбор основной/fallback-модели или поведение guest mode.

## Decisions

### Единый snapshot и два режима доставки

Сборщик получает московские границы дня и строит snapshot из durable-запросов и текущего runtime-состояния. Автоматическая доставка проверяет `DailyAnalytics.reportSentAt` и после успешной отправки отмечает отчёт. Ручная команда использует тот же snapshot, но обходит только idempotency guard и не меняет `reportSentAt`.

Альтернатива — дублировать запросы и форматирование в scheduler и controller — отклонена, потому что ручной и вечерний отчёты быстро разойдутся.

### Авторизация и видимость команды

Доступ проверяется одновременно по private chat и `ctx.from.id === analyticsChatId`. Команда может не входить в общие command scopes; при необходимости её можно зарегистрировать только в owner-specific chat scope. Неавторизованные вызовы завершаются без аналитического ответа.

### Источник активности

Входящая активность считается по сохранённым `Message` с отправителем, отличным от bot user ID. Ответ считается по исходящему сообщению бота, связанному через `replyToMessageId`; пользователь для метрики ответа берётся из родительского сообщения. Для scheduler bot ID передаётся из инициализированной информации бота, а не угадывается по username.

### Идентификатор модели в Message

В `Message` добавляется nullable `modelId String?`. При сохранении обычного AI-ответа записывается точное значение `model.modelId`, например `google/gemini-3.7-flash` или `deepseek/deepseek-v4-flash`. Новые модели не требуют изменения Prisma enum. Старые записи и не-AI исходящие сообщения остаются с `NULL`.

Разбивка «дорогие/дешёвые» строится по текущему выбору основной и fallback-модели, а отчёт дополнительно показывает точные model IDs. Успешный ответ считается по сохранённому `Message`; неуспешные попытки считаются отдельно runtime-счётчиком.

### Runtime-счётчики

Небольшой модуль состояния хранит счётчики по ключу московской даты: vector searches, searches with hits, добавленные context messages, начатые/успешные/неуспешные AI-ответы и latency samples. При чтении snapshot проверяется московская дата; переход на новую дату создаёт пустое состояние. Ручной отчёт не очищает состояние.

После рестарта состояние начинается заново. В отчёте для таких полей указывается «с момента запуска процесса», чтобы не выдавать частичный день за полный. Vector context не сохраняется в БД, как было согласовано.

### Источники дополнительных метрик

- `QuotaUsage` остаётся источником распознавания image/voice и пользовательской `ANALYSIS`-квоты.
- `UserFact.createdAt` используется для новых фактов.
- `FactImpact.timestamp` используется для фактов, реально попавших в ответы.
- Уникальные чаты и пользователи считаются агрегатами по `Message`, без выдачи их ID в отчёт.
- Покупки, возвраты и активные подписки используют существующие запросы.

### Privacy boundary guest mode и /ask

Guest mode и `/ask` не превращаются в обычные `Message` только ради аналитики. `/ask` остаётся вне обычного отчёта. Guest mode сохраняет текущий `GuestInteraction`-контракт; его model ID не добавляется в эту первую миграцию, поэтому разбивка по `Message.modelId` относится к обычным сохранённым AI-ответам.

## Risks / Trade-offs

- [Старые записи не имеют model ID] → показывать их отдельно как `не определено`, не делать ретроактивных догадок.
- [RAM-счётчики теряются при рестарте] → явно маркировать неполный период; durable-метрики строить из базы.
- [Ответы модели могут быть сохранены с задержкой после доставки] → считать модельный ответ только после успешного `saveMessage`, а ошибки доставки/сохранения логировать отдельно.
- [Bot ID недоступен на слишком раннем startup-вызове] → получать его до первого analytics snapshot и передавать в сборщик явно.
- [Векторный результат может попасть одновременно в user и chat context] → считать добавленные результаты, а не обещать уникальные сообщения.
- [Среднее/p95 latency runtime-метрики неполны после рестарта] → добавлять в отчёт область действия счётчика и не смешивать её с durable day totals.

## Migration Plan

1. Добавить nullable `Message.modelId` и применить Prisma migration; старые строки не backfill-ить.
2. Добавить сохранение model ID для обычных AI-ответов и расширить repository input.
3. Реализовать durable aggregate queries и runtime counter с московской датой.
4. Перевести автоматический отчёт на общий snapshot builder.
5. Добавить owner-only `/analytics`, не меняя `reportSentAt`.
6. Запустить `db:generate`, `db:validate`, unit-тесты, typecheck и lint.
7. Для отката оставить nullable-поле без использования и отключить ручную команду; существующие данные и старый отчёт должны продолжить работать.
