# Proposal: Исправление логики распознавания изображений и обновление лимитов квот

## Summary

Реализация двух критических улучшений системы:
1. Распознавание изображений по всей цепочке reply (до 10 уровней) вместо только непосредственного reply
2. Изменение лимитов квот на финальные значения (платная подписка заменяет бесплатные лимиты, не прибавляется)

## Why

### Проблема 1: Ограниченный поиск изображений

Текущая реализация проверяет только непосредственный `reply_to_message` для поиска фото. Если пользователи ведут диалог с промежуточными сообщениями (A отправляет фото → B комментирует → C спрашивает бота), система не найдет фото от A.

**Пример:**
```
Пользователь_А: [фото] + "смотрите чего тут"
└─ Пользователь_Б: "да, интересно"
   └─ Пользователь_В: "ио, расскажи что это"
```

Текущая система: бот не найдет фото (смотрит только на сообщение Б).
Требуемое: бот должен найти фото от А, пройдя по цепочке В→Б→А.

### Проблема 2: Неправильное суммирование лимитов

Текущая реализация `getPersonalDailyLimits` складывает бесплатные и платные лимиты:
- FREE: PRIMARY=10, IMAGE=5, VOICE=5
- WEEK personal: PRIMARY=30, IMAGE=15, VOICE=15
- Итоговый лимит WEEK: PRIMARY=40 (10+30), IMAGE=20 (5+15), VOICE=20 (5+15)

Требуемое: платная подписка **заменяет** бесплатные лимиты:
- WEEK personal: PRIMARY=30, IMAGE=15, VOICE=30 (финальные значения)

### Проблема 3: Несоответствие закономерностей

Требуется:
- Personal VOICE = Personal IMAGE × 2
- Group PRIMARY = Group IMAGE
- Group VOICE = Group IMAGE × 2

## What Changes

### 1. Функция findPhotoInReplyChain (NEW)

Новая функция в `src/controllers/process-message.ts` для поиска фото в reply chain до 10 уровней.

### 2. Изменение :text handler

Использование `findPhotoInReplyChain()` вместо простой проверки `reply_to_message?.photo`.

### 3. Изменение :photo handler

Перемещение проверки `shouldRespond` ДО резервирования квоты IMAGE.

### 4. Изменение getPersonalDailyLimits

Возврат `freeLimits` (если нет подписки) или `sumLimits(subscriptions)` (если есть). БЕЗ сложения.

### 5. Обновление констант

- `freeLimits.VOICE`: 5 → 10
- Все `personal.VOICE`: IMAGE × 2
- Все `chat.PRIMARY_RESPONSE`: равно chat.IMAGE
- Все `chat.VOICE`: chat.IMAGE × 2

### 6. Обновление текста

"прибавляется к бесплатным" → "заменяет бесплатные" в subscription-presentation.ts

## Goals

### Основные цели

1. **Реализовать multi-hop поиск фото в reply chain**
   - Ходить по цепочке reply до 10 уровней
   - Использовать Telegram API и БД для недоступных сообщений
   - Находить фото в предках запроса пользователя

2. **Изменить логику применения лимитов**
   - Платная подписка возвращает свои лимиты (не free + paid)
   - Несколько подписок складываются (paid1 + paid2)
   - Без подписки возвращаются бесплатные лимиты

3. **Обновить значения лимитов**
   - Personal: FREE (10/5/10), WEEK (30/15/30), MONTH (50/30/60), QUARTER (100/50/100), YEAR (500/200/400)
   - Group: WEEK (3/3/6), MONTH (5/5/10), QUARTER (10/10/20), YEAR (20/20/40)
   - FREE VOICE: 10 (было 5)
   - Group PRIMARY: равен GROUP IMAGE (было меньше)

### Non-goals

- Изменение цен подписок (остаются 49/99/199/599 Stars)
- Изменение логики голосовых сообщений (только обновление лимитов)
- Добавление новых типов квот
- Изменение алгоритма резервирования/возврата квот

## Technical Approach

### 1. Функция findPhotoInReplyChain

Новая функция в `src/controllers/process-message.ts`:

```typescript
async function findPhotoInReplyChain(
  ctx: BotContext,
  startMessage: {...} | null | undefined,
  maxDepth = 10,
): Promise<{ photo: PhotoSize; messageId: number } | null>
```

**Алгоритм:**
1. Начать с `startMessage` (reply_to_message текущего запроса)
2. Проверить наличие фото в текущем сообщении
3. Если нет - перейти к reply_to_message
4. Если reply_to_message недоступно через API - обратиться к БД:
   - Найти replyToMessageId в таблице Message
   - Загрузить родительское сообщение
   - Проверить поле media на image/jpeg
5. Повторить до maxDepth или до нахождения фото

### 2. Изменение getPersonalDailyLimits

В `src/shared/quota-service.ts`:

```typescript
export function getPersonalDailyLimits(
  subscriptions: Array<{ plan: SubscriptionPlan }>,
): Record<QuotaKind, number> {
  if (subscriptions.length === 0) {
    return freeLimits;  // Только free
  }
  return sumLimits(subscriptions, 'personal');  // Только paid, без free
}
```

### 3. Обновление констант

`freeLimits`:
- PRIMARY_RESPONSE: 10
- IMAGE: 5
- VOICE: 10 ← было 5
- ANALYSIS: 1

`planDetails` - обновить все значения согласно таблицам в Goals.

## Impact

### Пользовательский опыт

**Положительное:**
- Более естественное распознавание изображений в диалогах (не нужен прямой reply на фото)
- Предсказуемые лимиты (то что видишь в тарифе = то что получаешь)
- Больше лимитов VOICE для всех (FREE 10 вместо 5)
- Больше лимитов PRIMARY для групп (равны IMAGE)

**Негативное:**
- Пользователи с WEEK могут увидеть уменьшение лимитов (было 40 PRIMARY, стало 30)
- Но: большинство пользователей выиграют от исправленной логики

### Техническое

- Новая функция добавляет 1-2 БД запроса на обработку текстовых сообщений с reply (только если нужно идти дальше по цепочке)
- Производительность: приемлемо (maxDepth=10, early exit при нахождении фото)
- Обратная совместимость: сохранена (те же API, только улучшенная логика)

## Alternatives Considered

### 1. Оставить суммирование free + paid

**Отклонено:** Усложняет расчёт и презентацию. Пользователи путаются: "У меня WEEK, почему 40 запросов а не 30?".

### 2. Ходить по всей истории чата для поиска фото

**Отклонено:** Слишком дорого по БД запросам. maxDepth=10 покрывает 99% реальных кейсов.

### 3. Индексировать все фото в чате

**Отклонено:** Избыточно. Нам нужны только фото в треде конкретного запроса.
