## Context

См. `proposal.md` для мотивации изменения. Сейчас `src/controllers/whats-new.ts` строит один глобальный текст с глобальными счётчиками, выбирает все групповые чаты и отправляет сообщение последовательно, продолжая работу после ошибки. В модели `Chat` нет состояния доставки. В таблице `Message` уже есть `chatId` и `sentAt`, а scheduler уже выполняет задачи под общим advisory lock.

## Goals / Non-Goals

**Goals:**

- Сделать текст What’s New актуальным и полностью заменить устаревшее содержание.
- Посчитать статистику пакетно по активным чатам и вставить её в сообщение конкретного чата.
- Исключать чаты с неудачной доставкой из последующих рассылок.
- Реактивировать чат после появления новых сохранённых сообщений.
- Сохранить текущие owner-only, confirmation, sequential delivery и completion report контракты.

**Non-Goals:**

- Не менять механику квот, подписок, web-доступа или распознавания изображений.
- Не отправлять в неактивный чат пробное сообщение для проверки доступности.
- Не добавлять отдельный persistent-признак успешности распознавания голоса: используется существующая семантика сохранённых входящих `VOICE` сообщений.
- Не менять поведение других фоновых рассылок и feature-флагов чатов.

## Decisions

### Состояние активности чата

Добавить в `Chat` поля `active Boolean @default(true)` и `inactiveSince DateTime?`. Одного boolean недостаточно: без времени деактивации ежедневная проверка не сможет отделить новые сообщения от истории чата.

При миграции существующие записи получают `active = true`, поэтому rollout не выключает текущие цели. При окончательной ошибке `sendPost` обновляется только соответствующий чат; ошибка обновления состояния логируется, а ошибка доставки всё равно остаётся недоставкой в итоговом отчёте.

Альтернатива — хранить только `active` и реактивировать чат при любом сообщении, обработанном контроллером. Она не соответствует требованию ежедневной проверки и не сохраняет границу «после ошибки», поэтому отклонена.

### Per-chat статистика и предпросмотр

Для активного набора целей получить две агрегированные выборки сообщений:

- ответы: `senderId = botUserId`, `replyToMessageId IS NOT NULL`;
- голосовые: `messageType = VOICE`, `senderId != botUserId`.

Обе выборки ограничиваются `chatId` активных групп и преобразуются в map `chatId → stats`. Это уменьшает число запросов по сравнению с двумя отдельными count-запросами на каждый чат. Для поиска новых сообщений после разных `inactiveSince` использовать один repository-level SQL `EXISTS`/`UPDATE` запрос с индексом `Message(chatId, sentAt)`, а не последовательный N+1 обход.

Предпросмотр остаётся единым для владельца: общий текст проверяется до подтверждения, а в реальных сообщениях каждому чату подставляются его счётчики. В preview следует явно пометить, что статистика в рассылке будет рассчитана отдельно для каждого чата, чтобы не выдавать статистику одного чата за глобальную.

`BroadcastConfirmation` хранит snapshot активных целей и подготовленное содержимое для каждой цели. Это сохраняет одноразовое подтверждение и не требует повторно вычислять или менять состав целей во время фоновой отправки.

### Деактивация после ошибки доставки

`runBroadcast` по-прежнему отправляет цели последовательно. После исключения из `sendPost` он:

1. сохраняет `active = false` и `inactiveSince = now`;
2. логирует chat id и причину ошибки;
3. увеличивает только счётчик недоставленных;
4. продолжает следующую цель.

Успешный fallback не деактивирует чат. После сохранения состояния чат не попадёт в новый snapshot целей, пока не будет реактивирован.

### Ежедневная реактивация

Добавить scheduler-задачу с timezone `Europe/Moscow`, выполняемую раз в сутки под существующим `withAdvisoryLock`. Она одним запросом на уровне репозитория находит неактивные групповые чаты, где существует `Message` с `sentAt > inactiveSince`, и атомарно возвращает их в `active = true`, очищая `inactiveSince`.

Имеющийся индекс первичного ключа `Message(chatId, id)` не оптимален для временной проверки, поэтому добавить индекс `Message(chatId, sentAt)` в рамках той же миграции.

Альтернатива — Telegram API-проверка `getChat` или отправка пробного сообщения. Она создаёт внешние запросы в каждый неактивный чат и не отвечает на требование «в чате появились сообщения», поэтому не используется.

### Источник текста и промо-дат

Новое сообщение хранится в `buildWhatsNewPost` как единый русскоязычный шаблон. Таблица «было → стало» использует значения, опубликованные предыдущим What’s New, а текущие цены акции фиксируются как 20% до `2026-08-31 23:59:59.999` по московскому времени: `49 → 39`, `99 → 79`, `199 → 159`, `599 → 479` ⭐.

## Risks / Trade-offs

- **[Временная ошибка Telegram или сети]** Чат будет исключён до появления нового сохранённого сообщения → это соответствует выбранному правилу деактивации, а ежедневная проверка ограничивает срок ручного восстановления.
- **[Сообщение появилось между preview и отправкой]** Счётчик snapshot может немного устареть → считать статистику непосредственно при подготовке подтверждения и явно показывать в preview, что значения per-chat.
- **[Большое число неактивных чатов]** Полный обход может создавать нагрузку → использовать `EXISTS` с индексом `(chatId, sentAt)` и один scheduler-запрос.
- **[Миграция активирует старые чаты]** После deploy все ранее существующие чаты снова будут целями → это безопасное default-поведение; только новые ошибки доставки их деактивируют.

## Migration Plan

1. Добавить `Chat.active`, `Chat.inactiveSince` и индекс `Message(chatId, sentAt)` Prisma-миграцией; существующие чаты мигрировать в `active = true`.
2. Обновить repository API для выборки активных целей, per-chat статистики, деактивации и реактивации.
3. Заменить шаблон What’s New и изменить preview/broadcast на per-chat содержимое.
4. Добавить обработку деактивации в broadcast loop и ежедневную scheduler-задачу.
5. Выполнить focused-тесты, typecheck, lint и проверку миграции.

Rollback кода безопасен при сохранении новых колонок: старый код их не использует и продолжит видеть все чаты. Откат самой миграции удалит сохранённое состояние неактивных чатов и индекс, поэтому выполняется только при необходимости и после проверки отсутствия зависимости runtime от этих полей.
