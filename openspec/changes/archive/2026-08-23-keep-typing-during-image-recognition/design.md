## Context

См. `proposal.md` — Why. Обычные text/photo-контроллеры уже отправляют одно раннее действие `typing`, но heartbeat внутри `aiController` создаётся только после завершения поиска и распознавания изображения. Поэтому длинный pre-AI этап остаётся без обновлений статуса.

В проекте есть отдельные voice, guest и `/ask` потоки с собственным поведением. Новый жизненный цикл должен применяться только к обычному text/photo потоку, который уже прошёл проверку `shouldRespond`.

## Goals / Non-Goals

**Goals:**

- Поддерживать один непрерывный heartbeat `typing` через pre-AI подготовку и AI-генерацию.
- Не создавать два независимых таймера для одного запроса.
- Сделать остановку статуса идемпотентной и безопасной при любом завершении обработки.
- Не блокировать обработку из-за ошибки Telegram Chat Action.

**Non-Goals:**

- Не добавлять сообщение «Распознаю изображение…» или другой placeholder.
- Не менять vision prompt, модель, квоты, reply-chain или кэш описаний.
- Не менять voice, guest mode и ephemeral-поведение `/ask`.
- Не добавлять API для явной остановки `typing`: статус прекращается отсутствием новых обновлений.

## Decisions

### Единый внешний lifecycle статуса

После определения `shouldRespond` обычный text/photo-контроллер создаёт небольшой lifecycle-объект статуса: он сразу делает best-effort `typing`, затем повторяет действие с безопасным интервалом около четырёх секунд и предоставляет идемпотентный `stop`.

Lifecycle охватывает весь участок от принятия ответа до возврата из `aiController`: поиск контекста, обход reply chain, резервирование IMAGE-квоты, vision API и генерацию ответа. Владелец lifecycle останавливает его в `finally`, поэтому одинаково покрываются успех, ошибка, отмена и ранний возврат по квоте.

### Передача владения в aiController

`aiController` получает необязательный уже запущенный lifecycle через свои внутренние options. Если lifecycle передан, контроллер не создаёт собственный heartbeat и не отправляет повторное немедленное действие. Если lifecycle не передан, существующее поведение контроллера сохраняется для других вызывающих потоков.

Так сохраняется единый источник обновлений без гонки двух интервалов и без разрыва между распознаванием изображения и началом AI-подготовки.

Альтернатива — держать отдельный heartbeat только вокруг `describeTelegramPhoto` — отклонена: она оставляет без покрытия обход reply chain, поиск контекста, квоту и переход к AI-контроллеру, а также создаёт риск разрыва между двумя владельцами статуса.

Альтернатива — публиковать текстовое сообщение о распознавании — отклонена: это возвращает промежуточный placeholder, от которого отказались в `stream-first-ai-replies`.

### Ошибки Chat Action не влияют на ответ

Каждое действие `typing` выполняется best-effort. Ошибка Telegram API логируется и не отклоняет основную обработку. `stop` очищает локальный таймер и повторно безопасен.

## Risks / Trade-offs

- [Более частые действия `typing` увеличивают число вызовов Telegram API] → использовать фиксированный интервал с запасом до истечения статуса и не создавать более одного heartbeat на запрос.
- [Ошибка первого действия оставит пользователя без индикатора] → продолжать heartbeat и логировать каждую ошибку, не блокируя vision или AI.
- [Один из ранних возвратов забудет остановить lifecycle] → создавать его после `shouldRespond` и закрывать единым `try/finally` вокруг всего обычного потока.
- [Внешний lifecycle будет ошибочно передан ephemeral-потоку] → ограничить его создание обычными text/photo-контроллерами и сохранить специальные ветки без изменений.
