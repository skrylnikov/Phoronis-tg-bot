## Context

`/readyz` сейчас сначала проверяет агрегированное состояние runtime и только затем обращается к PostgreSQL и TEI. После первой неуспешной проверки состояние зависимости становится `not-ready`, ранний выход блокирует дальнейшие проверки и процесс остаётся исключённым из Kubernetes Service до рестарта.

Runtime-состояние одновременно хранит внешние зависимости и lifecycle-компоненты: transport, update workers и job worker. Исправление должно обновлять зависимости, не обходя эти lifecycle-гейты.

## Goals / Non-Goals

**Goals:**

- Восстанавливать readiness на следующей успешной проверке PostgreSQL и TEI без рестарта процесса.
- Сохранить существующие startup и shutdown гейты.
- Использовать периодические Kubernetes readiness probes как механизм повторной проверки.

**Non-Goals:**

- Менять liveness probe, Kubernetes restart policy или deployment-конфигурацию.
- Добавлять фоновый retry-loop, новую зависимость или отдельную state machine.
- Настраивать timeout TEI или делать embeddings необязательными.

## Decisions

### Перепроверять восстанавливаемые зависимости в `/readyz`

Каждый readiness probe до начала shutdown проверяет PostgreSQL и TEI, обновляет их состояния, а затем вычисляет итог через существующее агрегированное состояние runtime. Поэтому восстановившаяся зависимость снова становится ready, но незапущенный transport или worker продолжает удерживать HTTP 503.

Альтернатива — отдельный background retry-loop — отклонена: Kubernetes уже повторяет probe, а второй цикл добавил бы состояние и синхронизацию без нового поведения.

### Не повторять запросы внутри одного probe

Одна readiness-проверка выполняет по одной существующей проверке зависимости. Временный сбой даёт HTTP 503, а следующий Kubernetes probe выполняет повторную попытку. Это сохраняет ограниченное время ответа и не маскирует реальную недоступность.

### Проверять восстановление последовательными вызовами

Regression-тест моделирует неуспешный и следующий успешный probe на одном экземпляре runtime state для PostgreSQL и embeddings. Он должен доказать переход `ready → not-ready → ready` и сохранение HTTP 503 при незапущенных lifecycle-компонентах.

## Risks / Trade-offs

- [Нестабильная зависимость вызывает readiness flapping] → каждый ответ отражает текущую проверку; настройка timeout остаётся отдельным изменением при подтверждённой необходимости.
- [Unready pod продолжает обращаться к зависимостям] → обращения ограничены частотой Kubernetes readiness probe и не содержат внутренних retries.
- [Проверки зависимостей успешны во время startup] → агрегированное runtime-состояние всё равно возвращает HTTP 503, пока transport и workers не готовы.

## Migration Plan

1. Выпустить обычную версию приложения без изменений схемы данных и конфигурации.
2. Проверить последовательность 503 → 200 после кратковременной недоступности TEI или PostgreSQL без рестарта Phoronis.
3. При регрессии откатить версию приложения; миграция данных не требуется.
