# Design

## Context

См. proposal.md. Анализ 30 публичных сообщений извлекает facts и aliases одной utility LLM. Факты сравниваются с top-5 embedding-кандидатами отдельным LLM-вызовом. Pino пишет JSON в production; надёжное хранение stdout за несколько дней не задаётся этим репозиторием.

## Goals / Non-Goals

**Goals:** сохранить простой flow, объяснимый по источнику и журналу, без дополнительных зависимостей и без изменений трёх существующих моделей генерации.

**Non-Goals:** новые Telegram-команды, UI/dashboard, изменение общей Memory, перенос счётчиков квот, проверка объективной истины вне переписки, автоматическая разметка качества самой моделью.

## Decisions

- `fetch` к `https://routerai.ru/api/v1/decisions`, model `typesafe/jev-1.13`, ключ из существующего config. Отдельный модуль с runtime-валидацией probability 0..1, ответов на каждый вопрос, модели и choices. Timeout 10 секунд плюс имеющийся AbortSignal. SDK и обновление AI SDK для одной операции не нужны.
- Источники сначала проходят существующие проверки ID/author/privacy. Jev получает исходный text вместо summary, если text есть, и только минимальный публичный reply-контекст. Кандидаты одного анализа проверяются пакетно. Факт: Noul о поддержке; alias: два Noul о принадлежности и пригодности обращения. Начальные консервативные пороги: принятие 0.9, отклонение до 0.1, остальное uncertain; alias addressing тоже 0.9. Это параметры политики, а не заявленная точность модели. `UserFact.confidence` не переопределяется без отдельного контракта агрегирования.
- Пары фактов оцениваются Choice: duplicate/contradiction/independent/unclear с порогом top probability 0.9. Проверки выполняются для всех найденных кандидатов, с приоритетом уверенного duplicate; при неоднозначном отношении новый факт пропускается. Время и субъект указаны в критериях. Текущий retrieval threshold/limit сохраняется; независимые факты могут быть созданы обычным путём. Изменение обстоятельств разных периодов не является автоматическим противоречием.
- Ошибка Jev прерывает текущую попытку и позволяет действующему job retry. Нельзя превращать недоступность в поддержку или отсутствие дубля. Ранее сохранённые валидные evidence сохраняют существующую идемпотентность.
- Один `DecisionReview` в PostgreSQL: runId, kind, source chat/message, userId, candidate, candidateType, requested/actual model, policyVersion, probabilities, thresholds, outcome, action, duration, optional comparison snapshot. Source relation с `onDelete: Cascade`, user relation с cascade; индекс createdAt и chatId/createdAt. Journal не входит в context/retrieval. Хранятся кандидаты, не копии сообщений; relation snapshot фиксирует прежнее утверждение для проверки перезаписи.
- Журнал сохраняет accepted/rejected/uncertain/error, затем фактическое действие и ID результата. Ошибка аудита non-fatal и видна в stdout. JSON-события содержат IDs, policy version, scores, model, latency и действие без текста и сырого ответа провайдера.
- Почасовая cleanup-задача имеет собственный advisory lock и lifecycle существующего scheduler. Срок 7 дней применяется также при чтении. `bun run jev:report -- --days 3 --limit 30 [--chat-id ...]` выводит русскую сводку и примеры с текущими публичными источниками; JSON-формат для дальнейшего анализа. Оператор сам размечает ошибки; отчёт не вычисляет accuracy без ground truth. Параметры валидируются, выборка ограничена.

## Risks / Trade-offs

- [Ошибки на русском, цитатах, сарказме, отрицаниях] → unit-сценарии и синтетический live smoke; оценка реального качества после накопления журнала.
- [Записи аудита содержат производные пользовательские сведения] → локальная БД, cascade удаления, 7-дневный срок, отсутствие текста в stdout/Langfuse.
- [Отчёт не отражает решения при ошибках записи журнала] → отдельные error events и явное ограничение покрытия в документации.
- [Обновление провайдера меняет вероятности] → фиксированная версия и запись фактического model snapshot/policy version.

## Migration Plan

Добавить только новую таблицу и связи, сгенерировать Prisma client, проверить миграцию на изолированной локальной БД. Production migration/rollout не входят в запрос. При следующем разрешённом deploy существующий migrate initContainer применяет добавочную миграцию. Откат приложения сохраняет таблицу и старые данные; разрушительная обратная миграция не требуется.
