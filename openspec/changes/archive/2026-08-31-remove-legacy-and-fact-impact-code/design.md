## Context

См. `proposal.md` — Why. Контур fact impact был добавлен как эксперимент: создание usage-записей не подключено к генерации ответов, текстовая классификация реакции больше не выполняется, а Telegram reaction updates не обрабатываются. Тем не менее таблица, scheduler, ранжирование и аналитика продолжают считать эти данные действующими.

Одновременно приложение запускает одноразовую миграцию `User.metaInfo` при каждом старте. Новый `UserFactEvidence` уже предназначен для множественных подтверждённых источников, но старые одиночные source-поля пока поддерживаются параллельно. Prisma migrations выполняются init-container до запуска новой версии, тогда как старый pod ещё может обслуживать запросы.

Рабочее дерево содержит незавершённые изменения предыдущего hardening change. Реализация должна удалить только пересекающиеся fact-impact/metaInfo части и сохранить остальные privacy/runtime исправления.

## Goals / Non-Goals

**Goals:**

- Удалить fact-impact как продуктовую и техническую подсистему без замены новым классификатором.
- Оставить один актуальный источник provenance фактов — `UserFactEvidence`.
- Удалить завершённую runtime-миграцию и подтверждённо недостижимый код.
- Выполнить физическую очистку схемы без несовместимости со старым pod.

**Non-Goals:**

- Не переписывать и не squashing существующую историю Prisma migrations.
- Не удалять `LEGACY_HISTORY`, embedding backfill, `FactHistory`, OpenSpec archive или Telegram fallback только из-за слова `legacy`/`migration` в названии.
- Не добавлять новый механизм реакций, usage tracking или заменяющую метрику.
- Не проводить deployment без отдельного явного разрешения.

## Decisions

### 1. Удалить fact impact целиком

Удаляются обработчик реакции на reply, domain/repository слой, scheduler-задача, lock key, аналитический запрос и все тесты, проверяющие этот контур. Из `UserFact` убираются `usageCount`, `lastUsedAt`, `impactScore` и relation с `FactImpact`; ранжирование остаётся на `weight`, `confidence`, типе, сроке действия и свежести.

Альтернатива — восстановить вызов usage tracking и Telegram reaction handler — отклонена: это создаёт новый продуктовый механизм вместо удаления неработающего эксперимента.

### 2. Не заменять «использовано фактов» приблизительной метрикой

Строка и запрос удаляются из дневной аналитики. Количество новых фактов остаётся. Подмена числом загруженных фактов или prompt-событий была бы другим показателем и сохранила бы ложную семантику.

### 3. Удалять legacy-данные только после явных data gates

Перед отключением `User.metaInfo` проверяется отсутствие непустых JSON payload. Если они есть, существующая сходящаяся миграция продолжает работу до нулевого результата; данные не отбрасываются.

Перед удалением `UserFact.sourceChatId/sourceMessageId` проверяется, что `UserFactEvidence` существует и для каждой заполненной legacy-пары имеется соответствующая evidence-запись. Новые и обновляемые факты после первого cleanup-релиза пишут только evidence.

`FactImpact` не мигрируется: источник новых записей не подключён, реакции недостоверны, а продукт больше не использует score.

### 4. Разделить code cleanup и destructive schema cleanup

Первый релиз прекращает все чтения и записи удаляемых таблиц/колонок, но оставляет физическую схему совместимой со старой версией. После подтверждения, что все pod работают на первом релизе, отдельная forward migration удаляет:

- таблицу `FactImpact`;
- `UserFact.usageCount`, `lastUsedAt`, `impactScore` и связанные индексы/relations;
- `User.metaInfo`;
- legacy `UserFact.sourceChatId/sourceMessageId`, их FK/index и старую relation сообщения.

Альтернатива — один релиз с `DROP` — отклонена: init-container применит migration до готовности нового pod и может сломать запросы старого pod.

### 5. Ограничить общий dead-code cleanup подтверждённым import graph

Удаляются пустая `/index`, `domain/language`, `analysis-limiter`, мёртвый `domain/user` barrel, связанные константы и экспорты без единого вызова. Перед удалением каждого leaf-экспорта повторяется repository-wide поиск; код с runtime-входом, package script или действующей спецификацией сохраняется.

## Risks / Trade-offs

- [В production остался неперенесённый `metaInfo`] → data gate блокирует удаление; миграция повторяется до нулевого остатка.
- [Не все legacy source-пары покрыты evidence] → остановить cleanup, выполнить идемпотентный backfill и повторить проверку.
- [Destructive migration применяется при старом pod] → не создавать и не публиковать второй релиз до подтверждённого rollout первого.
- [Удаление impact score меняет порядок фактов] → принять детерминированное ранжирование по уже действующим сигналам и закрепить его focused-тестом.
- [Статический поиск ошибочно считает entrypoint мёртвым] → учитывать package scripts, controller registration и dynamic imports перед удалением файла.
- [Rollback после `DROP`] → откатываться можно только к первому cleanup-релизу; возврат к более старой версии потребует новой forward migration, а не восстановления удалённых недостоверных impact-данных.

## Migration Plan

1. Подтвердить, что migration с `UserFactEvidence` применена, и снять counts для `metaInfo`, evidence gaps и `FactImpact`.
2. При ненулевом `metaInfo` или evidence gaps не продолжать destructive cleanup; довести текущие миграции до сходимости.
3. Реализовать первый релиз: удалить runtime fact-impact, ложную аналитику, `metaInfo` scheduler и подтверждённый dead code; перестать читать/писать legacy source-поля, сохранив колонки в БД.
4. Проверить typecheck, lint, unit/integration tests, Prisma generation/validation и OpenSpec; затем только по отдельному разрешению выкатить первый релиз и подтвердить pod/readiness/logs.
5. После полного rollout первого релиза добавить отдельную forward migration с `DROP`, обновить Prisma schema/generated client и повторить проверки.
6. Только по отдельному разрешению выкатить второй релиз и подтвердить отсутствие schema/runtime ошибок. Старые migration-файлы остаются неизменными.
