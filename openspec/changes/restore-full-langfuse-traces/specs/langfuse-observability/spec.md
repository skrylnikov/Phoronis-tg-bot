# Spec Delta

## MODIFIED Requirements

### Requirement: AI-генерации имеют коррелируемые Langfuse observations

Система MUST создавать root observation для каждой persisted chat- и guest-generation, если генерация не отключила сохранение ответа. Root MUST сохранять имена `chat-generation`/`guest-generation`, доступные `sessionId`/`userId` и связь с дочерними LLM/tools в одном trace. Guest generation MUST использовать guest query id как `sessionId`. Новое покрытие MUST ограничиваться этими ответами и вложенными LLM/tools.

#### Scenario: Обычная chat-generation создаёт trace

- **WHEN** обычный AI-запрос успешно проходит через генерацию с включённым сохранением ответа
- **THEN** в Langfuse появляется root `chat-generation` с `sessionId` текущего AI-треда и `userId` отправителя, если Telegram передал пользователя
- **AND** его LLM/tools связаны с тем же trace и доступны для просмотра из root

#### Scenario: Guest-generation сохраняет собственную корреляцию

- **WHEN** guest-запрос получает AI-ответ с включённым tracing
- **THEN** root `guest-generation` и его дочерние observations связываются с guest query id, не подменяя его session id обычного чата

#### Scenario: Генерация без persistence не создаёт обязательный trace

- **WHEN** вызывающий путь явно отключает сохранение ответа, в том числе `/ask`
- **THEN** ответ продолжает формироваться по текущему пути без нового tracing и записи input/output

#### Scenario: Другие AI-пути сохраняют текущее поведение

- **WHEN** выполняются отдельные vision-, voice-, фоновые AI-вызовы или context compaction
- **THEN** этот change не включает для них новое tracing-покрытие

#### Scenario: Параллельные ответы не смешивают контекст

- **WHEN** chat- и guest-запросы выполняются одновременно
- **THEN** каждый root и его LLM/tools сохраняют собственные trace/session/user attributes и собственную политику записи содержимого

### Requirement: Telemetry не раскрывает приватный контекст

Система MUST записывать очищенный model input/output неприватных chat/guest только в специализированные поля observations. Metadata и обычные логи MUST содержать только безопасные технические данные. В private mode root и все LLM/tools MUST исключать тексты, аргументы, результаты и приватный контекст, сохраняя метрики и причину исключения. Секреты, токены, бинарные вложения и служебные объекты MUST NOT экспортироваться в любом режиме.

#### Scenario: В trace попадает безопасная статистика

- **WHEN** chat-generation завершается
- **THEN** observation содержит latency и агрегированные размеры/счётчики текущего telemetry-контракта
- **AND** очищенные инструкции, сообщения и ответ неприватного запроса находятся в input/output, без дублирования в metadata или обычных логах

#### Scenario: Приватные данные не попадают в metadata

- **WHEN** контекст содержит имена пользователей, память, результаты поиска или сообщение пользователя
- **THEN** эти значения не сериализуются целиком в Langfuse metadata
- **AND** для неприватного запроса input отражает только данные, действительно переданные в соответствующий model call, без дополнительного чтения из базы

#### Scenario: Private mode исключает содержимое во всём trace

- **WHEN** chat/guest выполняется с включённым private mode, включая tool call или ошибку провайдера
- **THEN** root, generations, tools, события и error fields не содержат текстов запроса/ответа, истории, памяти или аргументов/результатов tools
- **AND** сохраняются технические метрики и явная причина отсутствия input/output

#### Scenario: Секрет встретился в тексте или результате tool

- **WHEN** экспортируемые данные содержат известный runtime secret, распознаваемый токен, Authorization, credential-bearing URL или подписанную служебную ссылку
- **THEN** секретное значение удаляется или заменяется маркером во всех экспортируемых полях до отправки
- **AND** исходные данные AI-вызова не изменяются

#### Scenario: В запросе присутствует вложение или служебный объект

- **WHEN** потенциальный telemetry payload содержит байты, base64/data URL, заголовки HTTP или Telegram/runtime context object
- **THEN** экспортируется только безопасное описание вложения либо маркер исключения, без бинарного содержимого, credentials и служебного объекта

### Requirement: Ошибка Langfuse не ломает AI-ответ

Система MUST рассматривать ошибки создания, обновления, очистки, сериализации и отправки telemetry как non-fatal для обработки Telegram update. Ошибка tracing MUST логироваться с безопасным техническим контекстом, а генерация и сохранение ответа MUST продолжаться, если сама AI-операция не завершилась ошибкой. Телеметрия MUST NOT повторно запускать модель или tool ради восстановления trace.

#### Scenario: Langfuse недоступен во время ответа

- **WHEN** отправка observation завершается сетевой ошибкой или Langfuse временно недоступен
- **THEN** пользователь получает обычный AI-ответ, ошибка tracing логируется, а update не падает только из-за Langfuse

#### Scenario: Подготовка telemetry завершается ошибкой

- **WHEN** очистка или сериализация observation не может завершиться
- **THEN** содержимое пропускается с безопасной диагностикой, а основной AI-вызов выполняется один раз и сохраняет своё обычное поведение

## ADDED Requirements

### Requirement: Chat и guest имеют читаемые Input и Output

Для успешного неприватного chat/guest root observation MUST содержать очищенный снимок фактических инструкций и сообщений первого LLM-шага в input и итоговый собранный ответ в output. Роли и порядок сообщений MUST сохраняться. Система MUST явно обозначать исключение или усечение содержимого, чтобы пустые поля и неполный контекст не выглядели успешной полной записью.

#### Scenario: Ответ без tools

- **WHEN** неприватный chat/guest получает текстовый ответ
- **THEN** root Input показывает инструкции, включая добавленные правила tools, и фактические сообщения в порядке отправки модели
- **AND** root Output содержит итоговый текст после завершения стрима, совпадающий с результатом генерации до Telegram-форматирования

#### Scenario: Большой input или output

- **WHEN** очищенный input либо output превышает предел записи
- **THEN** Langfuse получает ограниченный диагностический снимок с явным маркером усечения и исходным размером
- **AND** модель получает полный исходный запрос, а Telegram получает обычный ответ

### Requirement: LLM-шаги и tools представлены отдельными observations

Каждый фактический LLM-шаг chat/guest MUST иметь дочернюю observation типа `GENERATION`, а каждый выполненный инструмент — `TOOL` с именем и идентификатором вызова. Неприватные observations MUST содержать очищенные вход/выход соответствующего шага. Система MUST сохранять причинную связь между LLM и tools и MUST NOT создавать дубли одного шага двумя способами instrumentation.

#### Scenario: Модель использует инструмент

- **WHEN** модель вызывает tool и продолжает генерацию с его результатом
- **THEN** trace содержит первый LLM-шаг, tool с его очищенными аргументами/результатом и следующий LLM-шаг с фактическим контекстом
- **AND** число tool observations совпадает с числом выполненных вызовов, без повторного исполнения инструментов

#### Scenario: Инструмент возвращает ошибку

- **WHEN** tool выбрасывает ошибку либо возвращает структурированный результат с ошибкой
- **THEN** tool observation отражает фактический неуспешный результат с безопасной диагностикой
- **AND** дальнейшее поведение модели соответствует существующему контракту обработки tool errors

### Requirement: Generations содержат фактическую модель и измеренные показатели

LLM observations MUST содержать фактическую модель/провайдера, доступные параметры генерации, input/output/total tokens, finish reason и длительность. TTFT, reasoning tokens и cache read/write MUST записываться при наличии измерения или provider usage. Отсутствующие показатели MUST оставаться неизвестными. Суммарный usage MUST NOT удваиваться из-за повторной записи одного LLM-шага.

#### Scenario: Используется lite-модель

- **WHEN** квота выбирает lite-модель вместо основной
- **THEN** generation отображает фактически использованный model id и применённые параметры, включая доступный reasoning effort

#### Scenario: Многошаговая генерация возвращает usage

- **WHEN** ответ использует несколько LLM-шагов
- **THEN** каждый шаг содержит свой usage, а агрегированные показатели ответа соответствуют сумме шагов без повторного подсчёта
- **AND** стоимость отображается только при наличии достоверных цен и сопоставления модели; приложение не придумывает её из числа символов

#### Scenario: Cache usage не предоставлен

- **WHEN** RouterAI не возвращает cache usage или TTFT нельзя измерить
- **THEN** эти показатели отмечены как недоступные, а прочие измеренные метрики сохраняются

### Requirement: Ошибки и отмена завершают observations

Ошибка или отмена LLM/tool MUST завершать соответствующую observation и root с безопасным статусом и технической причиной. Частичный ответ MUST отличаться от успешного окончательного ответа и следовать той же политике исключения private payload. Завершение стрима MUST предшествовать успешному завершению observation; instrumentation MUST сохранять ограниченный graceful flush.

#### Scenario: Стрим прерван после первых токенов

- **WHEN** provider или abort signal прерывает генерацию после части ответа
- **THEN** generation и root завершаются со статусом ошибки/отмены и доступной длительностью
- **AND** допустимый частичный output обозначен как частичный; private payload отсутствует

#### Scenario: Последний observation ещё находится в буфере

- **WHEN** процесс получает SIGTERM после окончания ответа до периодического экспорта
- **THEN** существующий bounded shutdown пытается отправить root и дочерние observations без повторной генерации ответа
