# Spec Delta

## MODIFIED Requirements

### Requirement: Автоматическое наблюдение имеет проверяемый источник

Система MUST извлекать псевдоним, адресата и уверенность модели только из доступных публичных пользовательских сообщений и их публичного контекста. Адресат MUST принадлежать переданному набору известных пользователей, псевдоним MUST присутствовать в исходном тексте после нормализации, а источник MUST существовать в текущем чате и закреплённом наборе исходных сообщений или публичных replies задачи. Само наличие имени в summary ответа бота MUST NOT создавать evidence. Оценки вне `[0, 1]`, нечисловые значения и уверенность ниже `0.5` MUST NOT сохраняться. Система MUST NOT считать собственные ответы бота источниками и MUST NOT назначать псевдоним по одному факту reply без смысловой связи.

#### Scenario: Обращение в reply
- **WHEN** пользователь отвечает Александру «Санёк, привет», модель извлечения выделяет обращение к Александру с confidence `0.85`, источник и ID проверены, а Jev подтверждает принадлежность с вероятностью `0.95`
- **THEN** система сохраняет наблюдение связи «Санёк → Александр» с вероятностью принадлежности Jev `0.95`
- **AND** одно наблюдение остаётся кандидатом без независимого подтверждения

#### Scenario: Reply содержит третье лицо
- **WHEN** в reply Ивану написано «передай Саше привет», а принадлежность имени конкретному известному Саше не установлена
- **THEN** система не назначает Ивану псевдоним «Саша» и пропускает неоднозначное наблюдение

#### Scenario: Модель придумала ID или источник
- **WHEN** наблюдение содержит неизвестный ID, отсутствующее сообщение или псевдоним, которого нет в исходном тексте
- **THEN** система пропускает это наблюдение без сохранения связи и без потери других валидных наблюдений и фактов

#### Scenario: Бот повторил собственную догадку
- **WHEN** бот сам использовал имя «Санёк» в ответе
- **THEN** ответ не создаёт наблюдение и не усиливает уверенность

#### Scenario: Источник входящего обращения
- **WHEN** входящий публичный reply к исходному сообщению содержит подтверждённое обращение к его автору
- **THEN** evidence ссылается на фактический ID входящего reply и его автора; ID исходного сообщения не подставляется вместо него


### Requirement: Выбор обращения отделён от принадлежности псевдонима

Система MUST выбирать явное предпочтение владельца прежде автоматического псевдонима. Без явного предпочтения система MUST использовать только подтверждённый псевдоним с confidence не ниже `0.9`, минимум двумя авторами подтверждений, нейтральной оценкой пригодности всех зачтённых наблюдений и отсутствием запрета владельца. Среди подходящих псевдонимов система MUST выбирать по уверенности, затем числу подтверждений, свежести и стабильному порядку имени. При отсутствии подходящего псевдонима система MUST использовать допустимое имя из Telegram-профиля. Fallback MUST проверяться против запретов и отклонений владельца после нормализации; если безопасного имени нет, обращение MUST отсутствовать. Система MUST NOT приравнивать уверенность принадлежности к приемлемости обращения.

#### Scenario: Высокая уверенность у неприятного прозвища
- **WHEN** связь имеет confidence `0.99`, но прозвище признано неподходящим или сомнительным для обращения
- **THEN** оно не используется как обращение, хотя подтверждённая связь может использоваться для поиска

#### Scenario: Автоматическое привычное обращение
- **WHEN** «Шурик» имеет confidence `0.92`, два независимых автора, нейтральные наблюдения и нет явного предпочтения или запрета
- **THEN** бот может выбрать «Шурик» обращением по установленному порядку

#### Scenario: Имя профиля совпадает с запрещённым
- **WHEN** пользователь запретил «Шурик», а Telegram firstName тоже «Шурик»
- **THEN** выбранное обращение не равно «Шурик»; применяется допустимый fallback либо ответ без имени


### Requirement: Владелец может подтвердить имя или исправить его использование

Система MUST поддерживать явные просьбы текущего пользователя «называй меня …», «не называй меня …» и «это не мой псевдоним» в текущем чате. Первое действие MUST подтверждать связь с confidence `1` и выбирать единственное предпочтительное обращение; второе MUST запрещать обращение, не удаляя существующую подтверждённую связь для поиска; третье MUST отклонять связь для поиска и обращения. Сам запрет обращения MUST NOT подтверждать неизвестную связь. Эти действия MUST применяться без ожидания очередного фонового анализа, быть идемпотентными и сохранять более новое решение при повторной доставке старого. Автоматическое обучение MUST NOT отменять запреты, отклонения или предпочтение владельца; снять отклонение может новая явная просьба владельца. Однозначное действие и имя MUST определяться по текущей просьбе кодом. При точном совпадении система MUST NOT менять другой сохранённый alias по выбору модели; падежная форма MUST сопоставляться только с проверяемым единственным соответствием. При неоднозначности изменение MUST NOT выполняться без уточнения.

#### Scenario: Пользователь предпочитает другое имя
- **WHEN** пользователь просит «называй меня Саша» при ранее выбранном «Шурик»
- **THEN** «Саша» становится единственным предпочтительным обращением с confidence `1` уже для текущего ответа
- **AND** другие корректные псевдонимы остаются доступными для поиска

#### Scenario: Запрет обращения
- **WHEN** пользователь просит «не называй меня Шуриком» для известного псевдонима
- **THEN** бот прекращает такое обращение, сохраняя подтверждённую связь для поиска

#### Scenario: Ошибочная принадлежность
- **WHEN** пользователь говорит, что «Шурик» не его псевдоним
- **THEN** эта связь исключается из поиска и обращения и не восстанавливается поздним фоновым анализом

#### Scenario: Старая команда доставлена повторно
- **WHEN** после новой просьбы «называй меня Саша» повторно выполняется более старая просьба «называй меня Шурик»
- **THEN** актуальным остаётся обращение «Саша»

#### Scenario: Модель передала другое сохранённое имя
- **WHEN** просьба содержит «называй меня Саша» или «не называй меня Саша», а модель предлагает существующий «Шурик»
- **THEN** система применяет действие к запрошенному имени либо отклоняет несоответствующий tool-вызов, не меняя «Шурик»

#### Scenario: Проверяемая падежная форма
- **WHEN** просьба содержит «не называй меня Шуриком», а сохранённый «Шурик» является единственным проверяемым соответствием
- **THEN** запрет применяется к «Шурик» без назначения произвольного другого alias

#### Scenario: Однозначная просьба не требует выбора tool моделью
- **WHEN** writable-запрос содержит поддерживаемую явную команду владельца без неоднозначности
- **THEN** решение применяется до генерации и текущий ответ получает фактическое новое состояние

#### Scenario: Запись завершилась ошибкой или старое действие вытеснено
- **WHEN** сохранение не состоялось либо более новая команда уже действует
- **THEN** подтверждение различает ошибку, уже применённое действие и вытесненный запрос, не сообщая о несуществующем новом изменении


### Requirement: Обучение сохраняет действующие квоты и ограничения данных

Система MUST выполнять автоматическое обучение в существующем анализе закреплённых окон публичных сообщений, запускаемом каждые 30 сообщений автора с квотой `ANALYSIS`, включая ограниченный публичный reply-контекст в обе стороны. Система MUST NOT добавлять отдельный платный анализ каждого сообщения или автоматический полный разбор прошлой переписки. Пассивно найденные имена MUST становиться доступными после успешного анализа, а явные изменения владельца MUST обрабатываться в текущем запросе.

#### Scenario: Квота анализа исчерпана
- **WHEN** наступает очередной запуск, но квота `ANALYSIS` недоступна
- **THEN** новые псевдонимы автоматически не извлекаются и дополнительный LLM-вызов в обход квоты не выполняется
- **AND** ранее сохранённые связи остаются доступны по обычным правилам

#### Scenario: Восстановление пропущенного обучения
- **WHEN** оператор повторяет FAILED-анализ исторического окна
- **THEN** псевдонимы извлекаются из источников этого окна, учитываются по исходным датам и не отменяют актуальные решения владельца

### Requirement: Jev независимо проверяет автоматическое наблюдение
Система MUST проверять принадлежность кандидата конкретному участнику по публичному источнику и отдельно пригодность для уважительного обращения. Для принятого evidence MUST использоваться вероятность принадлежности Jev; её MUST NOT подменять метрикой confidence выбранного варианта. Вероятность принадлежности MUST быть >= `0.8` включительно; пригодность обращения MUST оцениваться независимо по порогу `0.8` включительно (policyVersion 2). Действующие правила агрегирования, двух независимых авторов, квот и предпочтений владельца MUST сохраняться; накопленный рейтинг для автоматического обращения MUST оставаться >= `0.9`.

#### Scenario: Упоминание третьего лица в reply
- **WHEN** в reply написано «передай Саше привет», а LLM назначила адресату псевдоним «Саша»
- **THEN** Jev не подтверждает принадлежность лишь по наличию reply и evidence не сохраняется

#### Scenario: Принадлежность подтверждена, обращение сомнительно
- **WHEN** вероятность принадлежности проходит порог, а пригодность обращения не проходит отдельный порог
- **THEN** связь может накапливать evidence для поиска, но наблюдение помечается непригодным для автоматического обращения

#### Scenario: Прямое обращение проходит порог v2
- **WHEN** корректный incoming reply получает вероятность принадлежности `0.83` и пригодности `0.88`
- **THEN** evidence сохраняется с фактическим источником reply и neutralForAddressing true
- **AND** поддержка `0.799` не позволяет сохранить evidence
- **AND** одного автора по-прежнему недостаточно для автоматического подтверждения связи

#### Scenario: Явное решение владельца
- **WHEN** владелец явно задаёт, запрещает или отклоняет псевдоним
- **THEN** действующий инструмент применяет решение немедленно без ожидания фоновой проверки Jev
