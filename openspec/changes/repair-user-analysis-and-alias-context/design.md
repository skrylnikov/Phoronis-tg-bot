# Design

## Context

См. proposal.md — Why. `scheduleUserMessageAnalysis()` считает сообщения автора в чате и ставит задачу каждые 30. Payload содержит только userId/chatId/isGroup; claimed job не возвращает createdAt. Выполнение заново читает последние 30 сообщений, добавляет только родителя каждого reply и при отсутствии квоты возвращается без ошибки, что worker считает успехом. Legacy production выполняет aliases после обработки facts; новая локальная версия уже использует utility model registry и Jev. Строка `The operation timed out.` не устанавливает этап сбоя.

`getAliasContext()` отдаёт выбранное обращение вместе с внутренними статусами всех aliases. `set_my_alias` допускает любой существующий alias вместо запрошенного; fallback профиля не проверяет запреты. Compaction дедуплицирует контекстные снимки по первому появлению, теряя повторные обновления. Активный tracing-change пересекается по AI-файлам, но не решает фоновые таймауты.

## Goals / Non-Goals

**Goals:** воспроизводимое окно и bounded reply-контекст; восстановление только потерянной работы; сохранение авторства, квот, порядка evidence и команд владельца; техническая диагностика, позволяющая доказать исправление timeout.

**Non-Goals:** новая очередь или framework; неограниченный backfill чата; бесконечный replay; морфологический движок; автоматическое доверие ответам бота; произвольное редактирование сохранённых событий; deployment и production replay в рамках создания proposal или локального apply без отдельного запроса.

## Decisions

### 1. Закрепить ID источников в существующем payload

Версионированный payload анализа содержит `windowVersion`, `baseMessageIds`, `cutoffAt`, после подготовки — `replyMessageIds` и признаки усечения. ID передаются строками. Новые base IDs выбираются при постановке задачи с устойчивым порядком `sentAt DESC, id DESC`; модель получает хронологический порядок. Граница дополнительного контекста равна исходному createdAt задачи. Не хранить текст в payload: при каждой попытке проверять существование, чат, авторство и `private === false`.

Legacy payload обновляется условно в рамках принадлежащей worker lease: взять до 30 сообщений автора с `sentAt <= original createdAt`, упорядочить одинаковые даты по ID и закрепить набор до AI. Передать исходный createdAt через claimed job. Legacy-восстановление является приближением: удалённые сообщения и поздно поступившая историческая переписка не позволяют доказать первоначальные 30; это показывается в dry-run. Отсутствующие источники не заменяются свежими. Пустое доступное окно завершать как явно наблюдаемый `skipped_no_sources` без вызова модели и расхода квоты.

Альтернатива — только cutoff без ID — не защищает от позднего поступления и изменения выборки; хранение полных сообщений дублирует данные и усложняет удаление private-источников.

### 2. Один уровень публичных replies и два набора evidence

Для base IDs пакетно получить публичных родителей и входящие `Replies`, отфильтровать чат, дату `<= cutoffAt`, private и botId, дедуплицировать по ID. Начальные пределы: до 60 дополнительных сообщений, до 24 000 символов дополнительного текста. Сначала включать непосредственных родителей, затем входящие replies в стабильном хронологическом порядке; усекать целыми сообщениями, не подменяя текст evidence. При выборе incoming reply сохранять доступность его base-родителя; предел не уменьшает основное окно. Закрепить selected reply IDs и признак усечения перед AI; поздние ответы не появляются на следующем retry. Предел основного prompt измеряется отдельно, превышение не маскируется под пустой успех.

Передавать явные `MESSAGE_ID`, `AUTHOR_ID`, `REPLY_TO_MESSAGE_ID` и направление связи. `baseMessages` являются единственными источниками обычных facts; `aliasSources` включают base и выбранные публичные дополнительные сообщения. Исходники всегда берутся из реально существующих строк, не из summary диалога бота. Jev получает конкретный alias source, его публичный родитель и ID обоих авторов. Проверки extracted IDs и repository допускают входящий reply как фактический источник, а не подставляют ID base-сообщения. Текст исходника предпочтительнее summary; summary не расширяет допустимый источник.

Альтернатива — просто добавить replies к строке prompt — оставляет прежнюю карту ID и приводит к отбрасыванию корректных aliases. Обход всех descendants не нужен: он расширяет стоимость и вводит неоднозначные отношения.

### 3. Восстановление через существующий worker

Добавить команду `analysis:retry` с обязательным `--chat-id`, необязательным `--user-id`, пределом `--limit` (по умолчанию 10, максимум 100), фильтром диапазона исходного createdAt и явным `--apply`; без него всегда dry-run. Preview читает БД, перечисляет task IDs, даты/размеры окон, ошибки по технической категории и план усечения; AI не вызывается. Применение выбирает только `USER_MESSAGE_ANALYSIS/FAILED`, сортирует от старых к новым и условно возвращает выбранные строки в PENDING, сохраняя ID, dedupeKey, createdAt и окно. SQL-условие повторно проверяет FAILED; затронутые другим worker строки пропускаются.

У существующей задачи начинается новый ограниченный цикл error-попыток; сохранить предыдущие attempts и категорию ошибки в bounded replay metadata payload, сбросить attempts текущего цикла и lease, назначить availableAt. Не менять payments или другие статусы. Планирование от старых окон не гарантирует порядок завершения при нескольких workers, поэтому защита facts остаётся атомарной и независимой от очереди. После частичного успеха evidence дедуплицируется существующими ограничениями.

Не создавать replay-копии задач: они дублируют identity и усложняют подсчёт. Не добавлять recurring automation или автоматический terminal reset.

### 4. Квота и отмена являются результатами выполнения

При `reservation.allowed === false` handler возвращает отложенный исход с next availableAt в следующем дне Europe/Moscow. Worker условно переводит только принадлежащий ему analysis job обратно в PENDING; quota deferral не увеличивает error-attempts. Существующий handler-result можно расширить минимально, не переписывая платежный runner. Следующая попытка заново резервирует обычную квоту текущего дня, исторические quota counters не изменяются. Пустое окно пропускается до резервирования.

Передавать worker signal в extraction, Jev, embeddings и проверки перед каждой новой мутацией. Потеря lease и shutdown отменяют внешние операции; начатая ранее DB-операция может завершиться, поэтому частичные записи обязаны оставаться идемпотентными. Не считать wrapper `abortable()` полноценной отменой внутреннего promise.

### 5. Timeout исправляется по измеренному этапу

Ввести корреляцию job/attempt/run и этапы `window`, `extraction`, `verification`, `fact_relation`, `embedding`, `persistence`. Записывать модель, количества, длительность, категорию ошибки и stage; не писать source/prompt/ключи в обычные логи. Provider error сохранять с безопасной технической причиной, а не только общей строкой. Повторяемые и неповторяемые ошибки различаются без ослабления verification.

В начале apply измерить реальный bounded анализ и локализовать timeout. Затем устранить измеренную причину: например, некорректный transport/structured-output контракт, повторный зависший вызов или последовательный рост операций — только если это подтверждено. Начальный total budget попытки 180 секунд, extraction 60 секунд, отдельные verification/relation вызовы 30 секунд; существующий TEI timeout сохраняется. Все вызовы ограничены также остатком total budget. Число внутренних provider retry учитывать в том же budget; не добавлять второй неограниченный retry поверх worker. Эти ceilings уточняются по реальному замеру; бизнес-пороги меняются только по явному решению владельца продукта.

Смена utility-модели уже запланирована другим change; она не доказывает исправление. Обязательная приёмка — реальное извлечение + Jev + сохранение на контролируемом публичном/синтетическом окне, с результатом и latency по этапам. Production credentials и private payload не копируются в документы.

### 6. Исторические facts не отменяют новые

Для применяемого противоречия сравнивать ключ источника `(sentAt, chatId, messageId)` с максимальным ключом доступного accepted evidence существующего факта. Проверять до присоединения нового evidence и повторять проверку внутри той же транзакции, которая изменяет content. Сериализовать запись на уровне пользователя через существующий advisory-lock pattern: это закрывает также гонки retry создания независимого факта и привязки evidence. Новое более старое противоречие возвращает `skipped_stale_source`, не меняет content, embedding или weight и не становится подтверждением действующего содержания. При отсутствии доступного порядка — `skipped_unknown_source_order`.

Смысловые разные периоды всё ещё оценивает Jev: хронологическая защита не объединяет автоматически независимые факты. Использовать имеющиеся source message/evidence, не вводить last-write-time как время факта. Дополнительное DB-поле не требуется, если существующие evidence позволяют транзакционно определить порядок. Проверить повтор создания после частично успешной попытки: сравнение фактов и создание выполняются так, чтобы одинаковый accepted source не создавал дубликат того же факта.

### 7. Явные команды и fallback определяет код

Вынести существующую грамматику команд владельца в общий разбор текущего оригинального text/caption; извлекать action и literal name без потери отображаемого регистра. Разбор запускается после существующей проверки, что запрос адресован боту; обычную реплику группы без обращения к боту не перехватывать. Поддержать префикс «Ио» и явное упоминание текущего бота, не удаляя произвольное имя другого участника. Проверки автора/чата, forward, quotes и readonly/guest сохраняются. Однозначную команду применить перед сборкой контекста/generation; один и тот же разбор использовать в tool, чтобы model input не выбирал другую операцию. Точное имя в просьбе имеет приоритет перед любым существующим alias.

Для согласованного случая «Шуриком → Шурик» использовать консервативную проверку форм существующих имён: небольшая таблица однозначных окончаний для известных canonical aliases, без общего морфологического engine и без fuzzy-поиска по произвольному префиксу. LLM может предложить существующий canonical alias, но код принимает его лишь при единственном проверяемом соответствии; неизвестная/неоднозначная форма требует уточнения без записи. «Саша → Шурик» не соответствует ни одной форме и не принимается. Для нового имени, дословно указанного в prefer, сохранять original literal после штатной валидации.

Результаты owner операции различают `applied`, `already_applied`, `superseded`, `error`. Для поддерживаемой самостоятельной команды формировать короткое подтверждение кодом из результата; для уточнения показывать отсутствие сохранения. Обновить контекст до любого AI-продолжения. Tool не повторяет уже обработанную операцию и не содержит произвольных instruction strings в результате.

`selectAddressing()` проверяет также fallback-профиль по нормализованным запретам: preferred → подходящий автоматический alias → допустимый firstName → допустимый username → `null` (ответ без имени). Не использовать строку «пользователь» как обязательное обращение. Запрет обращения не исключает подтверждённую связь из поиска.

### 8. Модели передаётся готовая проекция aliases

Общий `getAliasContext()` отдаёт `chatId`, `userId`, `addressing: string | null`, `identityAliases` (только подтверждённые связи, включая запрещённые для обращения), `blockedAddressingAliases`, `rejectedIdentityAliases`. Confidence, CANDIDATE, preferred и алгоритм ранжирования остаются внутри domain/repositories. `get_user_info` использует ту же проекцию после существующих membership/privacy-проверок; canonical candidates для owner-сопоставления читаются кодом отдельно.

Сохранённые старые события не переписывать. При следующем turn добавлять актуальную проекцию обычным USER_CONTEXT/CORRECTION, в том числе при несовпадении старой схемы. Уточнить короткую стабильную инструкцию о смысле полей и свежих данных; она не обещает механически гарантировать каждое имя в свободном тексте. Проверять обычный, guest, readonly, fallback и текущий результат операции. Это сокращает бизнес-решения модели, не требует regex-редактирования свободного ответа.

При compaction сохранить контекстные snapshots в исходном порядке, включая повторные одинаковые значения после промежуточного изменения. Самое маленькое исправление — убрать дедупликацию по первому появлению, а не вводить новый event-sourcing engine. Тест `A → B → A → B` покрывает boundary и fresh builder после рестарта. Summary диалога не становится источником aliases.

## Risks / Trade-offs

- [Risk] Reply-контекст увеличивает стоимость → один уровень, фиксированные пределы, batch-чтение, закреплённый набор и явное усечение.
- [Risk] Legacy окно восстановлено неточно → обозначать реконструкцию; ID закрепляются один раз, без обещания полной исторической выборки.
- [Risk] Поздний ответ к старому сообщению не попадает в это окно → будущие собственные окна автора reply продолжают обычное обучение; полный backfill не добавляется.
- [Risk] Исторические факты применяются параллельно → сравнение источников и запись атомарны; порядок queue не используется как защита данных.
- [Risk] Имена имеют неподдерживаемую морфологию → консервативное сопоставление и уточнение; не расширять запись на произвольные сохранённые aliases.
- [Risk] Повторы при постоянной нехватке квоты остаются в PENDING → явный deferred outcome/availableAt и ограниченная операторская выборка; quota обход отсутствует.
- [Risk] Реальный provider smoke недоступен → сохранить локальные проверки, оставить live-пункт открытым и не объявлять timeout исправленным по mocks.
- [Risk] Другие changes редактируют соседние файлы → перечитать diff до apply, сохранить model/Jev/tracing baseline и интегрировать только изменения этого change.

## Migration Plan

1. Выполнить локальный apply поверх проверенного dirty baseline; сохранить совместимость старых analysis payload и context snapshots. Новые окна и replay metadata использовать в существующем JSON.
2. Пройти unit, PostgreSQL integration и контролируемый реальный provider flow, записать технические результаты и открытые ограничения в validation.md без production-переписки.
3. После отдельного запроса на deployment проверить image, нужные уже подготовленные миграции Jev/model-routing и health. Не считать локальные changes развёрнутыми по их archive-статусу.
4. Получить dry-run выбранных production FAILED-задач, проверить реконструкцию и публичные входящие обращения. После отдельного запроса применить сначала одно ограниченное окно; проверить COMPLETED/явный исход, source evidence и сохранение aliases, затем расширить выбранную партию.
5. Откатить приложение на прежний image при необходимости; расширенный payload JSON не мешает старому worker, однако тот читает плавающее окно. При rollback не запускать восстановление и не удалять source/evidence или queue строки.


## Уточнения по результатам apply

- Сравнение JSONB-снимков канонизирует порядок ключей объектов, порядок aliases стабилен. Это устраняет лишние context events после чтения из PostgreSQL, сохраняя реальные повторные состояния.
- Jev получает `targetRelation`, вычисленное кодом по уже проверенным ID (`self`/`reply_to_target`). Его вопрос проверяет употребление имени о конкретном адресате, не юридическую истинность имени. Семантика третьих лиц остаётся за verifier.
- Новое literal имя в prefer сохраняется после валидации даже при окончании, похожем на падежное. Неоднозначное сопоставление с существующими canonical aliases и неизвестные формы исправления не записываются.
- Реальный smoke подтвердил accepted самоназывание, сохранение candidate, idempotent retry, owner change и compaction. При исходной policy v1 независимый incoming reply не проходил порог 0.9; результат повторной приёмки с policy v2 фиксируется в validation.md. Причина первоначальных production timeout без deployment/replay нового диагностируемого worker не установлена.

### Политика Jev v2

По явному запросу пользователя 5 октября 2026 года общий порог принятия Jev снижен с 0.9 до 0.8 включительно. Это относится к поддержке фактов, выбранному отношению фактов, принадлежности alias и пригодности обращения; отклонение остаётся <= 0.1. Audit записывает policyVersion 2 и фактические пороги, старые решения не переписываются. Правила двух независимых авторов, агрегирования, confidence >= 0.8 для подтверждения связи и >= 0.9 для автоматического обращения сохранены.
