## Context

См. `proposal.md` — Why. В обычном AI-потоке sink создаётся до начала текстового стрима и сразу публикует «Думаю…»: draft в личном чате или настоящее сообщение в группе. Затем накопленный текст редактирует уже созданную публикацию. `chatGeneration` вызывает callback только для непустых текстовых дельт, поэтому первый такой callback является естественной границей начала публикации.

Обычные text/photo-контроллеры выполняют часть долгих операций до вызова AI-контроллера. Поэтому один немедленный `typing` после определения `shouldRespond` нужен до поиска контекста или распознавания медиа; существующий AI-level refresh должен продолжать поддерживать статус во время последующих этапов.

## Goals / Non-Goals

**Goals:**

- Отделить индикацию ожидания (`typing`) от публикации содержимого ответа.
- Сделать публикацию обычного sink ленивой: до первого непустого фрагмента Telegram не получает ответное сообщение или draft.
- Публиковать первый фрагмент сразу, а не ждать обычного интервала между обновлениями.
- Сохранить текущие правила rich Markdown, fallback, финализации, квоты и отмены.
- Не дублировать ephemeral-механику `/ask` и guest delivery.

**Non-Goals:**

- Не менять guest generation, guest query API или ephemeral-контракт `/ask`.
- Не менять отдельный voice flow с сообщением распознанного текста и последующим редактированием.
- Не вводить новое хранилище, миграции Prisma или внешние зависимости.

## Decisions

### Ленивое создание обычной публикации

Обычный sink создаётся без сетевого вызова публикации. До первого непустого update у него нет Telegram message ID. При первом update в группе отправляется reply с текущим накопленным текстом, а в личном чате выполняется первый `sendMessageDraft`. Полученная публикация сохраняется для последующих редактирований.

Альтернатива — оставить «Думаю…» и заменить его первым текстом — отклонена: она сохраняет лишнюю публикацию и не выполняет требование убрать placeholder. Альтернатива — всегда ждать финального текста — отклонена: она убирает видимый streaming UX.

Для специального ephemeral-пути `/ask` прежнее немедленное создание placeholder сохраняется отдельной веткой, поскольку этот placeholder является частью его адресованной пользователю доставки.

### Первый update публикуется немедленно

Пока публикация ещё не создана, throttling-интервал не применяется: первый непустой накопленный текст отправляется сразу. После создания публикации действующий интервал обновлений сохраняется. Если первый текстовый update не пришёл, `finish` отправляет итоговый ответ напрямую.

Это предотвращает задержку между фактическим началом текстового стрима и появлением ответа, не увеличивая частоту последующих Telegram API-вызовов.

### Typing начинается на границе принятого ответа

Для text/photo-потока немедленное действие `typing` выполняется после определения, что бот должен отвечать, но до поиска контекста, распознавания изображения и других долгих подготовительных операций. AI-контроллер продолжает периодическое обновление статуса во время собственной подготовки и стрима и очищает его при успехе, ошибке или отмене.

Повторное немедленное действие на границе AI-контроллера допустимо как best-effort обновление, но не создаётся второй независимый timer. Ошибка `typing` логируется и не блокирует ответ.

### Финализация остаётся защитным fallback

`finish` проверяет, была ли уже создана публикация. Если нет, он использует существующую финальную отправку rich/Markdown/plain ответа. Если публикация создана, он сохраняет текущую логику финального редактирования и fallback при ошибке форматирования. `cancel` для обычного потока не удаляет несуществующее сообщение; для `/ask` сохраняется удаление ephemeral placeholder при отмене.

## Risks / Trade-offs

- [Первый фрагмент может содержать незавершённый Markdown] → использовать существующие rich-message и MarkdownV2 fallback-ветки; финализация повторно применяет безопасное форматирование.
- [Telegram API может не принять первое редактирование или draft] → сохранить текущую обработку ошибок sink и финальную отправку как fallback; ошибка публикации не должна оставлять thinking placeholder.
- [Действие `typing` истекает или временно не принимается Telegram] → периодически повторять действие до завершения, логировать ошибки и не считать их причиной провала AI-ответа.
- [Часть подготовки выполняется до AI-контроллера] → выставлять первый `typing` сразу после решения отвечать в text/photo-контроллерах; voice flow остаётся отдельным и не расширяется этим change.
- [Пользователь увидит ответ только после первого непустого токена] → это намеренная граница: до неё показывается `typing`, а отдельное сообщение ожидания не создаётся.

## Migration Plan

1. Изменить обычный Telegram stream sink на ленивую публикацию и покрыть его сценариями private/group, no-chunk, rich formatting и error cleanup.
2. Перенести первый `typing` text/photo-потока до долгих подготовительных операций, сохранив один AI-level refresh lifecycle.
3. Обновить тесты контроллеров и специальных `/ask`/guest-путей, чтобы подтвердить отсутствие регрессий.
4. Запустить typecheck, lint и focused Vitest suite; затем проверить полный test/build gate проекта.
5. Для отката вернуть eager placeholder только в обычном sink и убрать ранний `typing`; схема БД и данные при этом не затрагиваются.
