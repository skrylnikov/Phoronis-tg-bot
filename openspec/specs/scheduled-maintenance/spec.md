# scheduled-maintenance Specification

## Purpose

Определяет надёжный lifecycle и взаимное исключение плановых задач, чтобы несколько экземпляров приложения не дублировали одну работу, а разные задачи не пропускали друг друга молча.

## Requirements

### Requirement: Каждая плановая задача имеет собственный distributed lock

Система MUST использовать стабильный отдельный advisory lock для каждого типа плановой задачи. Два экземпляра одной задачи MUST NOT выполняться одновременно, а разные типы задач MUST NOT блокировать друг друга только из-за общего ключа.

#### Scenario: Два экземпляра запускают одну задачу

- **WHEN** два процесса одновременно запускают одинаковую плановую задачу
- **THEN** ровно один процесс выполняет работу, а второй фиксирует пропущенный запуск

#### Scenario: Совпали расписания разных задач

- **WHEN** одновременно наступило время очистки private-сообщений и пересчёта fact impact
- **THEN** обе задачи могут выполняться независимо

### Requirement: Результат запуска отражает фактическое выполнение

Система MUST различать `completed`, `skipped` и `failed`. Неполученный lock MUST NOT логироваться или учитываться как `completed`; исключение внутри работы MUST иметь результат `failed` с именем задачи и длительностью без чувствительных данных.

#### Scenario: Lock уже занят другим процессом

- **WHEN** задача не получила свой advisory lock
- **THEN** система фиксирует `skipped` и не публикует событие успешного выполнения

#### Scenario: Задача упала

- **WHEN** выполнение завершилось исключением
- **THEN** система фиксирует `failed`, а следующий запуск по расписанию остаётся возможным

### Requirement: Scheduler принадлежит runtime lifecycle

Система MUST хранить handles всех зарегистрированных cron-задач, не регистрировать их повторно при повторном старте и MUST остановить их до отключения PostgreSQL и telemetry при graceful shutdown.

#### Scenario: Процесс получает SIGTERM

- **WHEN** начинается graceful shutdown
- **THEN** новые плановые задачи больше не запускаются, активные завершаются или отменяются по явному контракту, после чего закрывается БД

#### Scenario: Scheduler запускается повторно

- **WHEN** start вызывается второй раз в том же процессе
- **THEN** система не создаёт второй набор одинаковых cron-задач

### Requirement: Maintenance сходится с ограниченным объёмом работы

Плановая обработка растущих таблиц MUST выполняться set-based запросом или ограниченными batches и MUST NOT загружать всю историческую коллекцию в память. Одноразовая миграция MUST считать уже существующий эквивалентный результат выполненным и MUST безопасно сходиться после рестарта.

#### Scenario: Накопилась большая история fact impact

- **WHEN** запускается пересчёт score
- **THEN** система агрегирует или обрабатывает данные ограниченными порциями без загрузки всех impacts всех фактов одним запросом

#### Scenario: Факты из legacy metaInfo уже существуют

- **WHEN** миграция встречает эквивалентные ранее созданные факты без ошибок
- **THEN** пользователь считается успешно мигрированным и исходный legacy payload очищается
