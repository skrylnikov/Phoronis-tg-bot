# streaming-response-delivery Specification

## Purpose

Определяет предсказуемую публикацию обычных AI-ответов в Telegram через статус `typing` и первый фрагмент стрима без отдельного промежуточного сообщения.

## Requirements

### Requirement: Обычная обработка показывает статус typing

Для обычного текстового или медиа-запроса, который требует ответа бота, система MUST выставлять Telegram-статус `typing` после принятия решения отвечать и до публикации результата либо завершения обработки с ошибкой. Статус MUST поддерживаться повторными действиями во время долгой подготовки и генерации.

#### Scenario: Долгая подготовка ответа в личном чате

- **GIVEN** пользователь отправил сообщение, на которое бот должен ответить
- **WHEN** система выполняет поиск контекста, распознавание медиа или подготовку AI-запроса
- **THEN** Telegram получает статус `typing` до появления первого фрагмента ответа или завершения обработки

#### Scenario: Сообщение в группе не требует ответа

- **GIVEN** групповое сообщение не адресовано боту и не является reply на ответ бота
- **WHEN** система принимает сообщение
- **THEN** система не выставляет `typing` и не публикует AI-ответ

#### Scenario: Telegram не принял действие typing

- **GIVEN** Telegram API вернул ошибку на обновление статуса `typing`
- **WHEN** система продолжает обработку запроса
- **THEN** ошибка статуса не отменяет генерацию и доставку AI-ответа

### Requirement: Обычный поток не публикует thinking placeholder

Для обычных AI-ответов в личных чатах и группах система MUST NOT публиковать отдельный текстовый или draft-placeholder «Думаю…» до появления ответа модели.

#### Scenario: Подготовка ответа в группе

- **GIVEN** обычный запрос в группе принят к обработке
- **WHEN** модель ещё не выдала непустой текстовый фрагмент
- **THEN** в чате виден только статус `typing`, а сообщение «Думаю…» отсутствует

#### Scenario: Подготовка ответа в личном чате

- **GIVEN** обычный запрос в личном чате принят к обработке
- **WHEN** модель ещё не выдала непустой текстовый фрагмент
- **THEN** draft-ответ не создаётся и текст «Думаю…» не показывается

### Requirement: Первый фрагмент начинает публикацию ответа

Когда обычная генерация выдаёт первый непустой накопленный текстовый фрагмент, система MUST начать публикацию ответа этим фрагментом. В группе система MUST отправить одно reply-сообщение, а в личном чате MUST начать один draft. Последующие фрагменты MUST обновлять уже начатую публикацию и не создавать дополнительные сообщения.

#### Scenario: Первый фрагмент в группе

- **GIVEN** обычный запрос в группе находится в состоянии `typing`
- **WHEN** появляется первый непустой фрагмент стрима
- **THEN** бот отправляет reply с накопленным текстом фрагмента
- **AND** последующие фрагменты редактируют это же сообщение

#### Scenario: Первый фрагмент в личном чате

- **GIVEN** обычный запрос в личном чате находится в состоянии `typing`
- **WHEN** появляется первый непустой фрагмент стрима
- **THEN** бот начинает draft с накопленным текстом фрагмента
- **AND** последующие фрагменты обновляют этот же draft

#### Scenario: Богатое форматирование появляется во время стрима

- **GIVEN** накопленный текст фрагмента содержит Markdown, требующий rich-message или fallback-форматирования
- **WHEN** система публикует первый или последующий фрагмент
- **THEN** публикация использует существующие правила форматирования и не создаёт отдельный thinking placeholder

### Requirement: Финальный ответ публикуется без промежуточного фрагмента

Если генерация не выдала непустых промежуточных фрагментов, но вернула итоговый текст, система MUST отправить один финальный ответ обычным способом. При ошибке до публикации первого фрагмента система MUST NOT оставлять в чате промежуточное сообщение, созданное только для индикации ожидания.

#### Scenario: Модель вернула результат без text stream

- **GIVEN** обычный запрос принят к обработке
- **WHEN** генерация завершилась итоговым текстом без непустых stream updates
- **THEN** бот отправляет один финальный reply без предварительного сообщения «Думаю…»

#### Scenario: Ошибка до первого фрагмента

- **GIVEN** модель или внешний API завершились ошибкой до появления первого фрагмента
- **WHEN** система завершает обработку запроса с ошибкой
- **THEN** в чате не остаётся thinking placeholder, который нужно удалять
- **AND** существующие правила освобождения квоты и обработки ошибки сохраняются

### Requirement: Специальные режимы сохраняют отдельную доставку

Изменение поведения обычного потока MUST NOT менять guest mode и команду `/ask`. Guest query MUST по-прежнему отвечать через guest-механизм, а `/ask` MUST сохранять ephemeral-доставку, адресованную инициатору команды.

#### Scenario: Guest query в группе

- **GIVEN** Telegram update является guest query
- **WHEN** guest mode формирует ответ
- **THEN** ответ доставляется через guest-механизм без переключения на обычную публикацию группового AI-ответа

#### Scenario: Команда /ask в группе

- **GIVEN** пользователь запускает `/ask` в группе
- **WHEN** начинается генерация ответа
- **THEN** ответ остаётся ephemeral и адресованным пользователю, запросившему `/ask`

### Requirement: Финальная доставка соблюдает лимиты Telegram

Система MUST NOT передавать Telegram текст длиннее допустимого лимита выбранного метода. Полный итоговый ответ MUST доставляться в исходном порядке одним сообщением, одним rich-message либо lossless text document; форматирование MUST NOT создавать payload, превышающий лимит выбранного метода. Для режима, который не поддерживает подходящий fallback, система MUST использовать output budget 4096 tokens и MUST отклонить итоговый payload, если после форматирования он превышает 4096 символов.

#### Scenario: Обычный ответ помещается в legacy message

- **WHEN** итоговый текст после форматирования не превышает 4096 символов
- **THEN** система завершает доставку одним сообщением или редактированием текущего сообщения

#### Scenario: Ответ помещается только в rich-message

- **WHEN** итоговый текст превышает legacy limit, но допустим для rich-message
- **THEN** система может доставить его одним rich-message без legacy fallback с превышенным лимитом

#### Scenario: Ответ превышает максимум rich-message

- **WHEN** итоговый текст превышает лимит rich-message
- **THEN** система отправляет короткий reply в том же topic и прикладывает полный UTF-8 текст как document без потери содержимого

#### Scenario: Специальный режим не поддерживает продолжение

- **WHEN** `/ask`, guest или другой специальный transport допускает только ограниченный итоговый текст
- **THEN** generation использует budget 4096 tokens, а финальный guard не передаёт Telegram payload длиннее 4096 символов

#### Scenario: Финальная доставка не удалась

- **WHEN** Telegram отклонил итоговую часть после форматированного и plain fallback
- **THEN** обработка не помечается успешной, а ошибка остаётся доступной действующему retry-контракту
